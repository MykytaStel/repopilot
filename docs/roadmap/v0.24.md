# RepoPilot 0.24 — Calibrated Trust

Status: planned; approved direction, no implementation started. Target: tag
`v0.24.0` within three weeks of `v0.23.0` (by 2026-10-15).

Progress and evidence live in the
[v0.24 evidence ledger](../engineering/v0.24-evidence-ledger.md). This roadmap
is the release-level product contract; each phase gets a short specification
before code changes begin.

## What 0.24 Is Responsible For

RepoPilot 0.23 made `review` produce one bounded Change Proof. RepoPilot 0.24
makes that proof **mean what it says**:

1. **Calibrated priority.** A finding's priority reflects its severity and real
   urgency, and a CI gate on `P0`/`P1` fails for the reasons a maintainer would
   expect — not because a medium-severity structural finding happened to be new
   and in the diff.
2. **Honest, explained proof.** Every `limited`, `REVIEW`, or unmet obligation
   names its concrete cause and the one action that resolves it, grouped so a
   large change stays readable.
3. **Deeper semantic contracts.** Public API changes are typed beyond "a named
   export was removed", and the 0.23 contract families are validated on real
   repositories instead of fixtures alone.
4. **Measured quality, stated with its limits.** More rules carry labeled
   real-repository evidence; claims that rest on one reviewer or a small corpus
   say so.
5. **A release that publishes itself.** A tag publishes every channel through
   Trusted Publishing and verifies it by digest, with approval gates but no
   manual recovery.

Short name for the release: **Calibrated Trust** — the verdict, the priority,
and the release pipeline can be trusted without reading the implementation.

## Visible Difference From 0.23

| 0.23 | 0.24 |
|---|---|
| Priority is a pure score threshold; review context can lift any severity to P0 | Priority is capped by severity; review context raises urgency within that cap |
| `(limited)` coverage without saying why | Every limit carries a named reason and its fix |
| Proof obligations listed individually | Obligations grouped by check role with one action per group |
| Public-symbol contracts: removed named exports | Changed signatures, removed default/re-exports, and changed public types for TS/JS; public items for Rust |
| Contract families validated on fixtures | Contract families validated on labeled real-repository changes |
| Quality evidence for 6 of 54 rules | Evidence for at least 15 rules, each labeled with its power and reviewer model |
| Release recovery by hand | Tag publishes and verifies every channel; a rehearsal path exists before the final tag |

## Release Principles

- Keep 0.23's contract: local-only, deterministic, no source upload, no
  implicit command execution, no new top-level command.
- Change runtime behavior only with a before/after table on the zoo, the
  self-scan, and at least three real repositories.
- Treat every exit-code change as a compatibility event: CHANGELOG note,
  migration guidance, and a fixture pinning the new behavior.
- Fix what users see before adding what they have not asked for.
- Evidence tooling serves ledger rows; it does not grow on its own. Cap it at
  roughly one fifth of the release effort.
- Every PR updates its ledger row; the roadmap changes only when scope does.

## Phase 0 — Release Pipeline Closure

Make the next tag boring before any product change lands.

Deliverables:

- **Rehearsal path.** Support prerelease tags (`vX.Y.Z-rc.N`): GitHub Release
  marked prerelease, npm published under the `next` dist-tag (never `latest`),
  crates.io prerelease version, Homebrew tap untouched. The release contract
  rejects a prerelease that would move `latest`.
- **Automatic npm.** Prove on the first 0.24 rehearsal tag that
  `release.yml` publishes all six npm packages through Trusted Publishing with
  no manual dispatch (closes RP23-025).
- **Credential hygiene.** Remove the unused `CRATES_IO_TOKEN` secret; record the
  `HOMEBREW_TAP_TOKEN` expiry in the release checklist and fail the release
  contract early when a required secret is missing.
- **Parser upgrade.** Upgrade `tree-sitter` 0.26 → 0.27 (#438) behind a
  behavior freeze: full zoo byte-identical, language fixtures green.

Definition of done:

- one rehearsal tag publishes and verifies every channel without a manual step;
- `verify-publication.yml` passes for that tag;
- the tree-sitter upgrade changes no zoo snapshot.

## Phase A — Risk and Priority Calibration

Make `P0`/`P1` trustworthy enough to gate on.

Deliverables:

- **Severity ceiling.** A finding's priority cannot exceed the ceiling of its
  severity: `critical` → P0, `high` → P0, `medium` → P1, `low` → P2, `info` → P3.
  Context signals (baseline status, in-diff, graph hub, production role)
  reorder findings within the ceiling; they never cross it.
- **New `formula_version`.** Ship as `risk-v4`; JSON, SARIF, receipts, and
  history record it, and cached or stored `risk-v3` results are not reinterpreted.
- **Calibration evidence.** A generated before/after table of priority counts
  per rule on the zoo (default and strict), the self-scan, and three local
  repositories, committed with the change.
- **Gate compatibility.** `--fail-on-priority` and the Action gate keep their
  meaning (“fail at or above P*n*”); the CHANGELOG lists which findings stop
  gating and why.
- **Review urgency wording.** Human output stops presenting review priority as
  severity; the proof reasons name severity and priority separately.

Definition of done:

- no MEDIUM, LOW, or INFO finding is P0 anywhere in the calibration corpus;
- every CRITICAL/HIGH finding that was P0 in risk-v3 is still P0 or P1, and
  each downgrade to P1 is listed and justified;
- `scan` and `review` agree on the priority of the same finding occurrence
  unless review context legitimately raises it within the ceiling;
- risk calibration tests and scorecard are regenerated in the same PR.

## Phase B — Explained Proof at Real Scale

Make the 0.23 first screen hold up on large, unconfigured, real changes.

Deliverables:

- **Named limits.** `Evidence scope` shows the reason for `limited`
  (`no verification check configured`, `N excluded by size`, `unsupported
  language`, …) instead of the bare status.
- **Grouped obligations.** Proof obligations are grouped by check role
  (`test`, `build`, `lint`, `type-check`, …) with counts and one next action per
  group; JSON keeps every obligation.
- **Setup path.** When no check is configured, the next action shows the exact
  `repopilot init --suggestions-output` result for the detected stack, and the
  docs walk from first `review` to first `VERIFIED` in under five minutes.
- **Large-diff performance.** Add a real-repository review budget (100–200
  changed files) to the performance matrix; profile and fix the dominant cost
  so that the 122-file dogfood case runs at least 2× faster.
- **Projection parity.** Console, Markdown, HTML, JSON, SARIF, MCP, and the
  Action show the same named limits and grouped obligations.

Definition of done:

- the dogfood set (RepoPilot, three local repositories, two zoo repositories)
  shows no unexplained `limited` and no ungrouped obligation list on the first
  screen;
- the new large-diff budget is enforced in CI;
- a first-time user reaches `VERIFIED` on a sample repository by following only
  the printed next actions.

## Phase C — Deeper Semantic Contracts

Type the changes reviewers actually ask about.

Deliverables:

- **TypeScript/JavaScript public API.** Detect changed exported function
  signatures (parameter count, optionality, rest parameters), removed default
  exports, removed or renamed re-exports, and removed exported types, with
  resolved local consumers. Unsupported forms (overloads, conditional types,
  dynamic exports) stay explicit `limited`.
- **Rust public items.** Removed or re-signed `pub fn`/`pub struct` fields in a
  crate's public surface, with consumers resolved through the existing Rust
  import evidence.
- **Real-repository validation.** Label contract observations from real merged
  changes for the dependency, delivery, runtime-config, and security/test
  families; publish per-family counts with their denominators (RP23-008).
- **Parity.** Full, changed, cold-cache, and warm-cache paths produce identical
  contract evidence (existing review-zoo parity fixture extended).

Definition of done:

- every new contract kind has an unsafe fixture and a near-identical safe guard;
- no new contract kind can produce `BROKEN` without a resolved consumer;
- each validated family reports labeled real-repository observations, and any
  false positive found is fixed or documented as a limitation.

## Phase D — Measured Quality, Solo-Realistic

Grow evidence where it changes decisions, and label its strength honestly.

Deliverables:

- **Rule evidence.** Raise default-profile rules with labeled real-repository
  evidence from 6 to at least 15, prioritizing the rules that fire most in the
  default profile. Each rule reports its denominator, Wilson interval, and the
  small-sample boundary (RP23-013, RP23-010).
- **Reviewer model.** Until a second reviewer exists, use a blinded,
  time-separated single-expert protocol and label every result
  `single-expert, exploratory`. Independent two-reviewer adjudication remains
  the closure bar for broad precision claims.
- **Differential utility.** Run one frozen, pre-registered comparison of
  RepoPilot against the repositories' existing checks on fixed revisions,
  reporting novel actionable evidence, duplicate work, and time to first useful
  evidence (RP23-014), marked exploratory.
- **Scope cap.** No new evaluation harness unless it closes a ledger row.

Definition of done:

- the generated rule scorecard shows at least 15 rules with evidence and states
  the reviewer model and power for each;
- the differential packet validates with the recomputing validator;
- release notes make no claim beyond these measured, labeled results.

## Phase E — Agent Review Workflow

Serve the core use case — reviewing changes a coding agent made — end to end.

Deliverables:

- **Snapshot loop.** `repopilot snapshot` before an agent run and
  `review --since-snapshot` after it produce a Change Proof whose next action an
  agent can act on without parsing prose (stable reason codes in JSON/MCP).
- **Hook recipe.** Refresh the Claude Code / agent guardrail guide
  (`docs/agent-guardrail.md`) for the 0.23 proof: which exit codes block, how to
  surface the next action, and how to keep the loop local and fast.
- **MCP ergonomics.** `repopilot_review_change` returns grouped obligations and
  named limits (Phase B) and a short machine summary sized for agent context.

Definition of done:

- a scripted agent-edit demo (existing Wagtail/PetClinic scenarios) runs the
  snapshot → edit → review loop and blocks on the unsafe change with a
  machine-readable reason;
- MCP and CLI JSON agree on verdict, reasons, and grouped obligations.

## Phase F — Release Confidence

- Generated v0.24 release scorecard: calibration table, dogfood first screens,
  performance budgets, compatibility matrix, rule evidence, publication proof.
- Compatibility matrix extended with released `v0.23.0` producers and readers.
- Full gates plus `verify-publication.sh` for the final tag.

## Compatibility Contract

- No top-level command is added or removed; existing flags keep their meaning.
- **Priority is the one intended behavior change.** It ships as `risk-v4` with a
  before/after table and CHANGELOG migration notes; finding IDs, baseline keys,
  and occurrence identity do not change.
- Report schema changes stay additive (new reason codes, grouped obligations,
  named limits); a schema bump is made only if a field's meaning changes.
- Stored history and receipts produced with `risk-v3` remain readable and are
  labeled with their formula version rather than rescored.

## Non-Goals

RepoPilot 0.24 does not add:

- hosted services, telemetry, source upload, or an embedded LLM;
- autofix or implicit command execution;
- new top-level commands or a plugin runtime;
- new languages without fixture and zoo evidence;
- broad precision, recall, or competitor claims from single-reviewer or small
  samples;
- evaluation harnesses that do not close a ledger row.
