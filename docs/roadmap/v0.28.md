## Product outcome

RepoPilot 0.28.0 will extend change review across test helpers, local data-flow
boundaries, C/C++ includes, and Rust public APIs. Users should see more direct
evidence about which changed contracts still have local consumers, where
untrusted input reaches a dangerous operation, and where tests lost checks.
Analysis stays local, deterministic, bounded, and explicit about unresolved
language semantics.

This is a substantial approved scope with four product slices plus evidence,
performance, client, and release-readiness work. Each slice has a bounded
design and focused regression cases in place. Real-repository and release
evidence remain open. If a candidate cannot be supported soundly, record the
reason and replace it with another evidenced capability of similar user value;
do not silently shrink the release to documentation or evidence collection alone.

## Proposed product slices

### RP28-01 — Cross-file test-integrity analysis (P1)

Extend changed assertion-helper analysis beyond JS/TS to Python and Go. When a
changed local helper loses assertions or weakens supported matchers, identify
unchanged tests that import and call that helper. Preserve the current
same-file accounting and avoid guessing through ambiguous imports, re-exports,
dynamic dispatch, or unresolved package roots.

Acceptance:

- Each language has a real motivating change, a positive fixture, and controls
  for unchanged checks, safe helper refactors, ambiguous imports, and unrelated
  callers.
- Report the changed helper and affected test occurrence with stable path and
  line evidence; do not multiply-count a shared helper once per alias.
- Cover unchanged callers and moved or renamed tests. A moved test is treated
  as a changed caller and excluded from unchanged-test attribution. Exercise
  applicable cold/warm, changed-review, CLI, and MCP paths.
- Update the generated language-support and rule documentation from source-owned
  registries; do not claim general cross-file test analysis.

### RP28-02 — Bounded taint through local helper calls (P1)

Extend the existing intra-procedural taint analysis across a direct same-file
function boundary in JS/TS, Python, and Go. Track a tainted argument into a
uniquely identified local helper and to a supported SQL, command, or filesystem
sink; where the evidence permits, also track a helper return value back to its
caller. The depth limit is one helper boundary. No whole-program or
inter-file-call claim is included.

Acceptance:

- Implement source-to-sink cases grounded in real code for each supported
  language and sink family included in the release.
- Preserve parameterized-query, safe argument-vector, sanitizer, clean
  overwrite, unrelated-parameter, and unknown-call controls. Preserve simple
  identity-return taint through caller aliases and report when only the helper
  call changes while its sink remains unchanged.
- Keep taint on arguments passed through unknown calls and unmodeled helper
  return transformations. Classify combined or separated shell command flags,
  including PowerShell `-EncodedCommand`, without treating ordinary long options
  as command strings.
- Abstain on recursion, overloaded or ambiguous targets, dynamic dispatch,
  unresolved aliases, and unsupported control flow.
- Show source, helper parameter/return, and sink evidence; verify deterministic
  output and CLI/MCP parity.

### RP28-03 — Local C/C++ include impact (P1)

Add bounded repository-local include edges for C and C++ source and header
files, then use those edges in changed-file impact paths. Start with quoted
includes that resolve uniquely relative to the including file or repository
root. System includes, macro-generated include names, compiler flags, and
platform-specific search paths remain unresolved unless an explicit supported
configuration model is designed.

Acceptance:

- Cover `.c`, `.cc`, `.cpp`, `.cxx`, `.h`, `.hh`, `.hpp`, and `.hxx` where
  applicable, including nested local includes and a direct impact path.
- Preserve duplicate-candidate ambiguity and never fetch headers or invoke a
  compiler during analysis.
- Include missing, system, macro, path-traversal, and cyclic-include controls.
- Exclude quoted includes inside conditional-compilation branches unless a
  supported configuration model proves which branch is active.
- Label graph results as static include relationships, not runtime reachability
  or compiler-equivalent dependency resolution.

### RP28-04 — Rust public enum-variant contracts (P2)

Detect a removed public Rust enum variant when a surviving local file-backed
caller still constructs or matches that variant. Use the existing Rust
public-function and public-struct contract model and retain exact declaration
and caller evidence.

Acceptance:

- Cover tuple, struct, and unit variants only where a unique enum and module
  path are established, including a uniquely imported type alias.
- Preserve safe controls for coordinated caller edits, private enums,
  same-spelling variants on other enums, macros, `cfg`-gated declarations,
  re-exports, and ambiguous paths.
- Do not claim downstream breakage without a local caller; disclose the
  repository-only boundary.
- Version the report schema only if the new evidence cannot fit the existing
  additive contract, and retain supported-reader compatibility.

## Evidence and release workstreams

### RP28-E01 — Review-quality measurement (P1)

Expand reviewed evidence for the release's test-integrity, taint, and local
contract signals. Reproduce each candidate on the 0.27 baseline before a rule
change. Add and label real positive and safe-control examples; keep denominators
and selection methods explicit. For default-visible zoo changes, bless snapshots
and update every expectation label. For strict-only rules, use deterministic
sampling and keep hand-picked anchors separate.

### RP28-U01 — First-use and MCP client validation (P1 gate)

Collect at least two independent first-review observations before the 0.28.0
stable release, continuing toward the longer target of five. Product coding
proceeded at the owner’s direction while this gate remains open. In an available compatible MCP client, observe
approval, decline or cancellation, stale-workspace behavior, and unsupported
client behavior where applicable. Record client/platform versions and outcomes
without personal details. Scripted tests remain compatibility evidence, not
independent user observation.

### RP28-P01 — Performance and cache parity (P1 gate)

Compare the 0.28 candidate against the 0.27 baseline on matched review and scan
workloads. Include small and large repositories, changed and full scans, and
cold and warm cache paths where affected. Record repeated medians, variance,
memory, and complete semantic-output parity. Keep existing absolute budgets and
investigate regressions instead of widening limits.

### RP28-R01 — Release automation and publication (P1 gate)

Have the repository owner replace or validate the Homebrew tap credential and
rehearse the automatic formula update before a stable tag. The release workflow
must update the tap without manual recovery, use published asset checksums, and
pass the public-channel verifier for GitHub, crates.io, npm, and Homebrew.

## Shared constraints

- Keep review local; do not download dependencies or execute project code during
  analysis.
- Preserve deterministic findings, bounded work, safe abstention, and exact
  evidence identity. Generic finding deduplication must not use stable ID alone.
- Add unsafe, safe, and false-negative regression controls for every behavior
  change. Cover changed/cache/MCP paths when affected.
- Keep public report compatibility; any schema change needs an explicit
  migration and supported-reader evidence.
- Update the changelog and generated references when user-visible behavior is
  implemented. Update this scope and its ledger in each implementation PR.

## Proposed sequence

1. Scope approval is complete. Implementation began at the owner's direction
   while the two-observation RP28-U01 gate remains open.
2. Establish real-case baselines and bounded designs for each product slice;
   targeted local fixtures currently support the implementation boundaries.
3. Complete RP28-01 through RP28-04 as independently reviewable slices; keep the
   generated documentation and evidence ledger current.
4. Measure quality and performance against 0.27, then complete client and
   publication rehearsals.
5. Run the full pre-release gate and dogfood review when the candidate is ready
   for handoff; bump package versions and prepare release notes only then.

## Out of scope

- Compiler, build-system, or runtime-equivalent analysis for any language.
- Whole-program, inter-file, recursive, or unbounded taint propagation.
- External dependency resolution, network access, or automatic execution of
  suggested checks.
- Broad detector-count or accuracy claims without a defined measured corpus.
- New top-level CLI commands.
