## Technical scope

### RP25-T01 — Resolver input freshness and semantic parity

The TypeScript resolver's process-wide alias cache is keyed by repository root
in [ts.rs](../../src/graph/resolver/ts.rs). MCP scans execute in the same
process. No invalidation path was found in the source audit, but stale behavior
has not been reproduced: begin with a failing regression, not an assumed fix.

Acceptance:

- Within one MCP process, effective resolver-input changes from creating,
  editing, or deleting tsconfig.json or jsconfig.json update the resolved edges
  and their downstream evidence. Pin readable tsconfig.json precedence over
  jsconfig.json: edits to the inactive config preserve edges, and deleting the
  preferred config uses the existing jsconfig.json fallback.
- Config-only changes and switching an alias target do not retain stale edges
  or invent a broken import/export when the new target remains valid.
- Unchanged inputs can reuse cached work. A warm run agrees with a fresh-process
  run for the same scope, profile, configuration, and selected checks.
- Compare normalized semantic findings and signals, including severity,
  confidence, every evidence path/line/snippet, graph edges, proof coverage,
  reasons, and next actions. Normalize root paths, timings, handles, and cache
  telemetry. Full and changed scopes retain their intentional differences.
- Preserve the existing graph/cache invalidation contract and performance gates.

If a reproduction establishes that the current path is already correct, record
that evidence and close the suspected gap without inventing a behavior change.
An implementation spec chooses content-based invalidation or scan-owned state
after the reproduction. No public command or schema change is assumed.

### RP25-T02 — Direct JS/TS default-export removal

This is the smallest extension of the named-export contract, carried from
RP24-010. [JavaScript symbol facts](../../src/analysis/symbols/javascript.rs)
currently discard default exports and imports; the
[API-contract tests](../../src/review/signals/api_contract/tests.rs) pin that
exclusion.

Acceptance:

- A removed default export is reported when a surviving relative default import
  resolves to that exact local module, with caller and exporter evidence.
- Preserve a default export, coordinate the caller update, or remove the caller:
  each is a safe control. Uncertain forwarding, unsupported forms, and parse
  failure stay explicitly limited rather than proving a broken contract.
- CLI review and MCP retain the same semantic signal and occurrence evidence;
  applicable changed/cache paths agree. Both supported JavaScript and TypeScript
  forms have positive and safe fixtures.
- Attach labeled real-repository cases with their selection method and
  denominators before claiming precision or usefulness. Synthetic fixtures alone
  establish the supported contract, not production accuracy.

Parameter-type changes, exported types, deep forwarding, and comprehensive
re-export resolution are separate work. Do not turn this into a language-wide
API diff.

### RP25-T07 — Quiet fallback review candidate

The signal points at the changed empty JS/TS `catch` or pass-only Python
`except` and includes the call/import and later-return locations. Its evidence line
must be part of the diff, including when only the Python handler body changed.
It identifies a path worth checking; syntax alone cannot establish whether the
caught operation is required or whether the fallback result is incorrect. CLI
and MCP must preserve the same signal record.

The signal does not change full-scan findings or review-gate behavior. Its
fixture evidence proves the documented syntax contract only; independent
production labels and first-user usefulness remain separate evidence.

### RP25-T08 — MCP verification consent boundary

The [approved design](../engineering/v0.25-mcp-verification-consent-design.md)
defines check-specific MCP approval. No configured command may start from an MCP
tool call until a matching accepted form-mode response authorizes it.

Acceptance:

- Negotiate form-mode consent only for protocol `2025-11-25` with client
  capability `elicitation.form`; otherwise preserve static review and report
  each selected check as skipped.
- Show check ID, resolved program, exact arguments, working directory, and the
  host-permission/no-sandbox boundary. Do not send environment values or output;
  warn that credentials must not be placed in program or argument fields.
- Decline permits the next check; Elicitation cancellation, timeout, or invalid
  response stops later prompts while static review completes. MCP tool-call
  cancellation aborts the call. Correlate only the exact pending JSON-RPC
  response ID.
- Before execution or cache reuse, revalidate the reviewed workspace revision
  and the complete effective check policy from the original config source,
  including the resolved executable's SHA-256 content identity. Skip unresolved
  executables.
- Keep CLI verification behavior unchanged. Test accepted, denied, unsupported,
  malformed, cancelled, timed-out, interleaved, and stale-input paths with
  process sentinels.
- Preserve PATH symlink aliases in `argv[0]` for dispatcher commands such as
  Cargo/rustup; cover the behavior in both CLI and approved MCP verification.

This is a per-call user-mediated boundary, not a sandbox or cryptographic proof
of user intent. Verify real client UI behavior before making compatibility
claims.

## Follow-on technical work

RP25-T09 is the next independent engineering PR after the current T07
extension. Give RepoPilot a small, deterministic first-party verification
policy so dogfood can report actual check results instead of “not configured.”
Ordinary reviews must never launch checks implicitly; CLI users select IDs, and
MCP clients still require T08 per-check consent. Then validate Elicitation in
at least one real MCP client and record its version and UI behavior. A later,
separate design should assess OS-level process isolation and executable
pinning, including symlink retarget races, scripts/interpreters, and child
processes. Current per-call consent does not contain an approved process or
close those gaps.

The [358-PR article](https://dev.to/cherven/358-pull-requests-that-changed-tests-agents-rarely-weakened-them-they-bent-the-code-instead-3ld)
and controlled pilot motivate broader work beyond T07. Candidate follow-ups
include Promise `.catch`, error-sentinel patterns, more languages, and
independently labeled production cases. Do not expand detector scope until each
new syntax has unsafe and legitimate-recovery controls and a clear
evidence/confidence contract. The pilot and the 358-PR corpus do not by
themselves establish that any individual fallback is harmful.

## Verification and release boundaries

- Run focused regressions first, then the required handoff checks. Compare
  full/changed/cache only on semantically equivalent scopes or projections.
- Keep the current 123-file review median at or below 2,100 ms, the 20-file
  integrity review at or below 1,000 ms, and integrity share at or below 10%.
  Performance improvements need unchanged semantic evidence as well as timings.
- Report unresolved/unsupported imports and coverage honestly. Expanding language
  or taint claims requires frontend code, safe/unsafe controls, and measured cases.
- Preserve local deterministic analysis, explicit host-check selection, and the
  distinction between RepoPilot processing and the agent/provider boundary.
- Record version, commit, configuration/profile, platform, and labeled evidence
  for each closed row. Publication and catalog acceptance are separate evidence.
- Cut a release when its user-visible slice is complete; later capabilities and
  incomplete measurement limit the claims rather than holding the release.
