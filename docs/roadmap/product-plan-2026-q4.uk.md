# RepoPilot: план корисного офлайн-продукту на зараз і найближче майбутнє

Дата: **2026-09-28**. Стан: **робочий продуктовий план, створений на запит користувача**.
Горизонт: поточний v0.24, наступні 2–4 тижні та умовний напрям на 1–3 місяці.
Основа перевірки репозиторію: `origin/main` на `5ff7cf2a`.

Ціль: RepoPilot має виправдовувати встановлення тим, що регулярно допомагає
зрозуміти зміни, помітити суттєву проблему або швидше вирішити, що перевірити.

доступною щодня, зокрема без інтернету.

реалізації. Він не означає, що всі перелічені можливості вже реалізовані або

## 1. Яким має стати продукт

Після власної зміни, роботи агента або отримання чужого PR людина запускає
RepoPilot і швидко отримує чотири відповіді:

1. Які наслідки цієї зміни потребують уваги?
2. Де саме є підстава так вважати — файл, рядок, зв'язок із залежним кодом?
3. Які перевірки справді виконані для цієї версії коду, а чого ми ще не знаємо?
4. Яка одна наступна дія зараз найкорисніша?

Для повторного використання достатньо однієї команди, налаштованого hook або
звернення агента через MCP. Новому користувачу не потрібно знати внутрішні
назви фаз, формули risk, ledger чи протоколи експериментів.

**Обіцянка встановлення:** менше часу на пошук важливого в diff і більше
конкретних підстав для рішення. Це має бути помітно на реальних змінах
користувача, а результати вимірювання мають показувати й невдалі сценарії.

**Принцип довіри:** позитивний результат стосується оголошеного обсягу та
сумісних доказів. `VERIFIED` не означає відсутність усіх можливих помилок.
Невідоме, непідтримуване та неперевірене відображається явно.

## 2. Для кого робимо перший повний сценарій

| Користувач | Регулярна проблема | Очікувана користь | Перша поверхня |
| --- | --- | --- | --- |
| Розробник, який працює з кодовим агентом | Агент змінив багато файлів; важко оцінити наслідки | Короткий огляд ризикових змін, конкретні докази й наступна дія | CLI, snapshot, MCP |
| Мейнтейнер, який приймає PR | Треба відокремити суттєві зміни від великого diff | Вплив на споживачів API, межі доступу, перевірки та причини обмежень | CLI, HTML, GitHub Action |
| Розробник без стабільного інтернету або з приватним кодом | Хмарний review недоступний або неприйнятний | Корисний локальний аналіз із підготовленого checkout | Нативний binary, локальні звіти |
| Відповідальний за якість або власник роботи підрядника | Потрібні зрозумілі питання до виконавця | Звіт із фактами, межами перевірки й посиланнями на код | HTML/Markdown, технічний reviewer поруч |

Перші два сценарії визначають пріоритети. Розширення аудиторії має спиратися
на реальні труднощі читання звіту. Зрозуміліша мова може допомогти менш технічній
людині, але інструмент не підміняє інженерну оцінку довільної системи.

## 3. Повний шлях користувача

### 3.1. Перший запуск

1. Установити готовий пакет або binary для підтримуваної платформи.
2. У локальному Git-репозиторії з доступною базовою ревізією запустити `repopilot review .`.
3. Побачити обсяг аналізу, конкретний висновок і одну наступну дію.
4. Якщо потрібне налаштування перевірок — виконати `repopilot init --suggestions-output .repopilot/init-suggestions.toml`.
5. Переглянути пропозиції, перенести прийнятий запис у `repopilot.toml` і вибрати його ID.
6. Запустити, наприклад, `repopilot review . --verify rust.test`, якщо саме такий ID прийнято.
7. Побачити справжній результат перевірки й решту обмежень. До `VERIFIED` можна дійти лише за відповідних доказів та політики.

Час конфігурації вимірюємо окремо від завантаження пакета, залежностей і
тривалості тестів. П'ятихвилинна ціль стосується підготовленого прикладу;
вона не є обіцянкою зібрати будь-який великий проєкт за п'ять хвилин.

### 3.2. Щоденний цикл із агентом

```text
Доступний локальний репозиторій
  → snapshot перед роботою
  → зміни людини або агента
  → review --since-snapshot
  → важлива знахідка / потрібна перевірка / сумісний доказ
  → пояснення й виправлення або явне рішення reviewer
  → повторний review
```

Snapshot уже існує. Треба завершити весь шлях, перевірити межі dirty/untracked
стану й зробити machine-readable причини зручними для клієнтів. Наявний
snapshot записує HEAD та ознаку dirty; він не зберігає повну копію початкових
незакомічених файлів. Не можна називати всі знайдені зміни роботою агента без
урахування цього обмеження.

### 3.3. Повторний запуск наступного дня

Прийнята конфігурація залишається у репозиторії. Користувач повторює review,
бачить нові важливі зміни та реальний стан перевірок. Кешовані докази явно
позначені й сумісні з поточною ревізією. Відомі прийняті проблеми мають
пояснену політику; нові прояви не повинні зникати через надмірне об'єднання.

## 5. Роль sandbox у всьому плані

Sandbox уже відповідає на значну частину питання «чи є користь і чи можна
довіряти результату». Повний ланцюг потребує кількох різних спостережень.

| Рівень | Запитання | Що використовуємо | Умова успіху |
| --- | --- | --- | --- |
| Виконання | Чи можна відтворити експеримент? | Sandbox lifecycle, pinned SHA/image, cleanup | Кожна потрібна фаза має очікуваний результат; unavailable пояснено |
| Виявлення | Чи бачимо конкретно внесену проблему? | Mutation + `expected_rule_ids` + baseline scan + negative control | Потрібний сигнал на порушенні; відсутність нового такого сигналу на безпечній парі |
| Proof | Чи правильно оцінюється зміна? | Controlled ChangeProof benchmark, review fixtures | Відомо неправильна зміна не отримує хибного підтвердження |
| Додаткова користь | Що дізналися понад наявні перевірки? | Differential collector, зіставні докази, labels | Є перевірений висновок щодо нової корисної інформації, дублювання та витрат |
| Практичне використання | Чи людина зрозуміла звіт і змінила дію? | Спостережуваний користувацький прохід | Людина самостійно виконує наступний крок і може пояснити чому |

Наприклад, ранній Express пакет має 4/4 успішних lifecycle cases. У його
збереженому звіті TP/FP/FN та додаткова користь залишаються unavailable.
Це корисний технічний результат, але він не підтверджує, що RepoPilot виявив
усі внесені проблеми. Пізніші exact-rule пакети вже мають правильні поля для
такої перевірки; їх потрібно довести до узгодженого й відтворюваного стану.

Docker oracle вже працює з `--network none` та `--pull=never`. Аналізатор
зараз запускається окремо на хості, а підготовка джерел може використати Git
clone. Перевірку офлайн-обіцянки доповнюємо для повного процесу аналізатора.
Звичайному користувачу RepoPilot Docker для CLI не потрібен.

Стандартний `--verify` запускає прийняті configured програми на хості;
його не називаємо ізольованим виконанням довільного чужого коду. Docker
sandbox тут є середовищем інженерних експериментів із визначеними командами.

## 6. Горизонти й порядок

| Горизонт | Результат для користувача | Робота | Умова переходу |
| --- | --- | --- | --- |
| Зараз: наступні 1–3 завершені PR | Можна почати review без здогадок; старі результати sandbox правильно зрозумілі | Setup path, узгоджений inventory, один свіжий контрольний запуск | Є працюючий сценарій і відтворюваний доказ його виконання |
| Найближчі 2–4 тижні | Можна користуватися офлайн; відома користь на конкретних змінах | Network-denied перевірки, differential labels, перші людські проходи, важливі noise fixes | Є спостереження користі та названі обмеження |
| Наступні 1–2 місяці | Зручний регулярний review агентських і командних змін | Agent loop, пріоритетні API-контракти, короткі пояснення, повторне використання | Користувачі повертаються й успішно завершують сценарії |
| До 3 місяців, за позитивних сигналів | Стабільний інструмент для обраної аудиторії | Політики команд, distribution polish, локальний перегляд за потреби | Доведена потреба в конкретних наступних можливостях |

Це порядок та орієнтир місткості роботи, а не обіцянка дат. Потрібні середовища,
учасники та незалежні оцінки можуть бути недоступні. Тоді продовжуємо інші
продуктові задачі, позначаючи відсутній доказ.

Поточний контракт v0.24 залишається джерелом релізного scope. Його наявна
ціль — 2026-10-15; весь цей багатомісячний план не стає вимогою до цього тегу.
Перенесення релізних пунктів робимо явно через контракт і ledger.

## 8. Потік B — перевірена офлайн-робота

**Результат:** із підготовленим binary, локальним checkout та потрібними
залежностями користувач може виконати заявлені локальні сценарії без мережі.

| Сценарій | Що перевіряємо | Правильний результат |
| --- | --- | --- |
| Binary + повний локальний checkout | `scan` та `review` під network deny | Аналіз завершується; немає неочікуваних мережевих спроб |
| Snapshot → локальні зміни → review | Git-ревізії та файли вже доступні | Заявлений обсяг правильно відображений |
| Локальний MCP | Stdio клієнт без зовнішньої моделі | Узгоджений із CLI висновок; процес MCP не потребує мережі |
| HTML/Markdown/JSON | Відкриття звіту офлайн | Зміст доступний, немає необхідних віддалених скриптів/ресурсів |
| Явно вибрана локальна перевірка | Інструмент і залежності підготовлені | Справжній pass/fail із сумісною ревізією |
| Відсутній executable або dependency cache | Перевірка не може почати/завершити роботу | Явна діагностика; немає `VERIFIED` завдяки цьому check |
| Недоступний Git ref / shallow або partial checkout | Потрібних об'єктів немає локально | Явне обмеження; відсутні об'єкти не перетворюються на чистий diff |
| Повторний запуск | Власний cache RepoPilot | Той самий зміст доказів за тих самих входів; кеш не приховує зміну |
| Налаштована команда потребує мережі | Зовнішня програма під обмеженням | Невдача/недоступність названа; static evidence залишається доступною |
| Новий комп'ютер | Перенесений офлайн-пакет + залежності | Встановлення та запуск перевірені окремо від звичайного runtime |

## 16. Метрики, які змінюють наші рішення

Цілі нижче — **пропоновані критерії pilot, не поточні результати**. Перед
вимірюванням зафіксувати версію протоколу, вибірку, завдання й пороги. Після
перегляду результатів не переписувати їх так, щоб невдала спроба стала успішною.

| Метрика | Як рахуємо | Початкова ціль / рішення |
| --- | --- | --- |
| Завершення first-use | Учасники, які завершили підготовлений setup task без підказки команди/ID, / усі спроби | Орієнтир 4/5; кожна невдача стає конкретним UX issue; це малий exploratory pilot |
| Час до першої корисної дії | Від початку локального завдання до підтвердженої учасником дії за коректною підказкою | Орієнтир до 5 хв на підготовленому прикладі; install, dependency fetch і check runtime окремо |
| Розуміння висновку | Людина правильно називає наступну дію та хоча б одне суттєве обмеження | Орієнтир 4/5; окремо фіксувати небезпечне надмірне трактування `VERIFIED` |
| Нові корисні докази | Оцінені actionable observations, не дубльовані зіставним baseline evidence | Показати чисельник, denominator і rationale; шукати повторення хоча б у двох репозиторіях перед розширенням сценарію |
| Дублювання | Зіставні дублікати / усі зіставні observations | Показати також частку unavailable comparison; не видавати різні ID за новизну |
| Шум | Default-visible findings, оцінені false-positive або непотрібними для поточного рішення | Показати окремо FP, valid-but-accepted і незрозуміле повідомлення; виправляти найчастіше |
| Повернення до використання | Добровільні повторні сесії протягом 7 днів | Початковий сигнал: 3/5 учасників; окремо показати тих, хто реально мав другу review-задачу, без приховування початкового denominator |
| Офлайн-виконання | Пройдені acceptance cases / заплановані cases для конкретного host | Усі обов'язкові cases; deliberate unavailable теж має бути правильним, але не рахується успішною перевіркою коду |
| Детермінізм | Ідентичний semantic projection на cold/warm повтореннях за pinned inputs | Нуль непояснених розбіжностей у committed контрольному наборі |
| Хибне підтвердження | Відомо проблемні контрольні зміни, яким видано несумісне позитивне proof | Нуль у заданому corpus; кожен випадок блокує claims відповідного сценарію до виправлення |
| Швидкість і RSS | Wall-time/RSS за workload, host, cold/warm і check policy | Зберегти existing CI budgets; не переносити число одного хоста на всі платформи |

Machine `evidence-ready`/`decision-ready` latency і час, коли людина отримала
користь, є різними вимірами. Таймер колектора не доводить людську економію часу.
Оцінки pilot із 5 людей, одного експерта або моделі не є репрезентативними
ринковими чи незалежними production precision/recall метриками.

## 17. Протокол реального користувацького проходу

### Спершу власні сценарії

- [ ] Вибрати 2–3 доступні власні репозиторії з різними типами змін; один прохід включає відключену мережу після підготовки.
- [ ] Зробити initial review без підказок поза документацією; записати всі місця зупинки.
- [ ] Пройти setup і вибір перевірки; спостерігати реальну дію користувача.
- [ ] Розглянути реальний diff після агента; записати, які повідомлення вплинули на рішення, а які дублювали очевидне.
- [ ] Повторити на наступній зміні; зафіксувати, чи з'явилося бажання використати інструмент знову та чому.

Це owner dogfood: автор уже знає продукт і не замінює нового користувача.

### Потім невеликий зовнішній pilot

Початковий розмір — приблизно п'ять добровільних учасників із цільової
аудиторії. Залучення людей та надсилання запрошень потребує окремої явної
авторизації; цей план сам по собі не є дозволом на повідомлення іншим.

1. Зафіксувати задачі до старту; використати prepared sample та одну дозволену реальну зміну.
2. Дати тільки install/usage docs. Допомогу дослідника записувати як допомогу.
3. Просити людину пояснити власне рішення; не підказувати бажану відповідь.
4. Зібрати конкретні дії, friction та рівень розуміння. Оцінка «подобається» недостатня.
5. Запропонувати користуватися протягом тижня; повернення має бути добровільним, без штучно нав'язаного другого завдання.
6. Звести факти, сильні/слабкі сценарії та наступний один UX або detection slice.

Локальний observation sheet містить лише потрібне: версію RepoPilot, host,
тип задачі, час/допомогу, причина review, виконана дія, оцінена користь,
нерозуміння та повторне використання. Приватний код, credentials і сирі
конфіденційні звіти в загальний репозиторій не копіюються. Автоматичної
телеметрії цей план не додає.

## 18. Рішення за результатами, включно з невдачами

| Спостереження | Наступне рішення |
| --- | --- |
| Sandbox lifecycle успішний, очікуваного сигналу немає | Перевірити signal expectation та supported scope; відтворити мінімальний випадок; виправити конкретний detector або явно обмежити capability |
| Artifact не проходить hash/schema validation | Знайти правильну immutable пару або recollect; не редагувати старий результат для проходження перевірки |
| Docker/image/dependencies недоступні | Зафіксувати prerequisite issue; продовжити незалежний setup/UX/fixture-review slice; не робити quality claim із цього випадку |
| Корисні докази є, setup складний | Наступний slice — onboarding; повторити той самий user task |
| Звіт точний, але людина не знає що робити | Переписати наступну дію/пояснення та перевірити розуміння |
| Багато valid-but-accepted findings | Переглянути default visibility/проектну політику, зберігаючи strict evidence |
| Додаткова користь не спостерігається | Звузити задачу та аудиторію; перевірити наступну обґрунтовану гіпотезу до розширення набору правил |
| Перший прохід добрий, добровільного повернення немає | Розібрати частоту потреби, витрати запуску та інтеграцію; не пояснювати це автоматично браком реклами |
| Виявлено false certainty | Виправити proof path, додати regression guard і звузити claims; інші verdict не використовувати для маскування помилки |
| Підтверджена користь і повторне використання | Посилювати успішний сценарій: точність, швидкість, інтеграція й наступна пов'язана capability |

## 19. Якість реалізації та релізні межі

Для кожної зміни:

1. Назвати конкретну проблему користувача та відтворюваний приклад до зміни.
2. Зробити мінімальний coherent slice; використати наявний canonical pipeline.
3. Перевірити значущі регресії й небезпечні близькі випадки; не додавати тести, що лише дублюють рядок реалізації без поведінкової користі.
4. Для noise/scan змін перевірити відповідні cache/full/changed paths і zoo labels.
5. Перед code handoff виконати доречний repo gate та dogfood `review . --base origin/main`; first screen має бути несуперечливим.
6. Оновити ledger evidence і user-facing docs/changelog за фактичною зміною.
7. Для PR/CI/release звірити конкретний commit і фактичний результат; draft CI може пропускати full release verification.

Для цього документа достатні перевірка Markdown-посилань, навігації,
release-contract та diff hygiene. Створення плану не потребує повторного
повного Rust або Docker запуску.

Межі поточної роботи:

- Репозиторії та runtime аналіз лишаються локальними; нової telemetry чи source upload немає.
- Перевірки — явно обрані configured commands; запуск не приховується у review/init.
- Правила, verdict, schema і exit-code зміни мають власні сумісність та acceptance evidence.
- Публікація npm/crates/GitHub tag та merge PR не є автоматичним наслідком підготовки плану.
- RC rehearsal використовує наявну prerelease pipeline; вимога не пересунути stable/default канали залишається обов'язковою.
- Широкі твердження про якість не з'являються з successful build, artifact validation або малого model-assisted pilot.

## 20. Організація роботи, щоб не застрягати

- Одночасно тримаємо одну основну продуктову зміну; незалежне читання evidence може йти поряд.
- На початку робочого циклу вибираємо не більш як три найближчі результати з черги Pxx.
- Завершення рахуємо за працюючим сценарієм та доказом, а не кількістю spec/plan/PR.
- Підготовлені specs та затверджений scope використовуємо повторно; новий документ потрібен, коли змінився суттєвий контракт або виявлено нову неоднозначність.
- Кожен implementation PR показує користувацький ефект: що стало простіше, якій проблемі запобігаємо або яке твердження тепер підтверджене.
- Evaluation tooling розширюємо лише для названої відсутньої метрики/ledger item; зберігаємо roadmap-орієнтир приблизно до 20% release effort на таке tooling.
- Не витрачаємо цикл на повторний повний gate без нових змін або причини сумніватися в попередньому результаті.
- Історичні артефакти не переписуємо; нова версія коду/manifest/label protocol отримує новий пакет із provenance.
- Щотижневий перегляд: що завершено для користувача, який доказ отримано, що змінило пріоритет і що стало зайвим. Автоматизацію для цього не створюємо без окремого запиту.

Виконавець реалізує й збирає артефакти; reviewer перевіряє зміст зміни;
користувач/учасник pilot оцінює зрозумілість і власну дію. Незалежні defect
labels мають відповідати заявленому протоколу — сама інша сесія агента не
перетворює оцінку на незалежне людське дослідження.

## 22. Напрям після перших доказів користі

Якщо повторне використання й цінність підтверджуються, розглядаємо:

1. Кращу навігацію локального звіту та пояснення на основі повторюваних user difficulties.
2. Переносні перевірені рецепти політик команд: checks, baseline, overlays, зрозумілі migration notes.
3. Додаткові semantic contracts у тих мовах/стеку, де наявні користувачі мають непокриті випадки.
4. Стабілізацію CLI, schemas і compatibility policy перед `1.0` на основі реального використання.
5. Тонку IDE/desktop інтеграцію лише тоді, коли доведено, що існуючі CLI/HTML/MCP поверхні створюють зайві кроки. Аналізатор і докази залишаються спільними.

До підтвердженої потреби не плануємо хмарний backend, обов'язкові облікові
записи, marketplace плагінів, масове додавання мов, embedded LLM або
автоматичне виправлення/merge. Кожна така можливість потребуватиме окремого
обґрунтування та обмеженого першого сценарію.

## 23. Що залишається невизначеним

| Питання | Як знімаємо невизначеність | Що робимо до відповіді |
| --- | --- | --- |
| Чи доступні всі pinned images і build dependencies зараз? | P02–P03 prerequisite inventory | Працюємо з доступними локальними прикладами, unavailable показуємо явно |
| Наскільки легко перенести ігноровані sandbox assets? | Reproduction recipe, immutable manifest/source/image identities | Зберігаємо наявну основну копію; не видаляємо старі пакети |

| Чи вистачає differential comparability для кожної метрики? | Existing identity adapters і recomputing validator | Вимірюємо доступні dimensions; решта unavailable |
| Чи є достатня додаткова користь для встановлення? | P05 + P06/P14, конкретні змінені рішення й повернення | Не стверджуємо ринкову перевагу; закриваємо найближчий supported use case |
| Чи потрібен окремий графічний застосунок? | User navigation/friction observations | Розвиваємо наявні CLI та локальний HTML у межах підтверджених проблем |

## 24. Словник для спільної роботи

- **Sandbox** — контрольоване середовище для повторення експерименту на відомому коді та зміні.
- **Oracle** — окрема перевірка очікуваної поведінки, наприклад test/build; її успіх сам по собі не означає правильності всіх findings.
- **Negative control** — близька безпечна зміна, на якій потрібний сигнал не повинен виникнути.
- **Holdout / evaluation** — випадки, відкладені для оцінювання; використання їх для tuning потрібно явно враховувати.
- **Differential utility** — вимірювання доданої користі поруч із наявними перевірками на тих самих змінах.
- **Provenance** — запис, звідки результат: версія коду, вхідні файли, команда, manifest, binary та hashes.
- **Valid artifact** — коректно оформлений і сумісний запис експерименту, який може містити failed або unavailable результат.
- **Exploratory** — корисний попередній висновок із названими обмеженнями; його не узагальнюємо на всі проєкти й користувачів.
- **Dogfood** — використання власного інструмента на своїх реальних задачах із фіксацією результату.
