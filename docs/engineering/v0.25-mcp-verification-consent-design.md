# RP25-T08 — MCP verification consent

Status: approved for implementation
Target: v0.25
Related scope: `docs/roadmap/v0.25.md`, `docs/engineering/v0.25-evidence-ledger.md`

## Problem

The `repopilot_review_change` MCP tool accepts configured verification-check IDs. A selected check is a local process that runs with the host user's filesystem and network permissions. The repository configuration defines the program, arguments, and working directory. MCP tool-call approval alone is not a distinct, check-specific confirmation that the user reviewed those details.

RepoPilot's stdio MCP implementation currently supports protocol revisions `2025-11-25` and `2024-11-05`, but does not process server-to-client requests or responses. Therefore it cannot ask the MCP client to present a check-specific user confirmation before execution.

## Outcome

A model or MCP tool call may request checks, but the request alone does not authorize their execution. RepoPilot asks the connected MCP client for one-time user consent to each selected check. A check runs only after an accepted form-mode Elicitation and only while the reviewed workspace and check definition still match the approved state.

If the client cannot provide that interaction, declines, cancels, times out, returns an invalid response, or the approved inputs change, RepoPilot does not start the process. Static review still completes and clearly reports that the check was not run, so the result remains unverified.

CLI `repopilot review --verify <id>` remains unchanged: selecting a check from the user's CLI is its existing explicit execution request.

## Design choices

1. **Per-call MCP Elicitation — selected.** Preserves MCP check execution while requiring the client to ask the user for each check. No approval persists after the tool call. Clients without the negotiated capability fail closed.
2. **Host-owned persistent allowlist.** Avoids a prompt per call, but introduces a second policy format and durable consent that can become stale. It is not selected for this slice.
3. **Remove MCP check execution.** Provides the smallest MCP attack surface, but removes an existing workflow. It remains a fallback if reliable user-mediated Elicitation cannot be implemented or tested.

The interaction follows form-mode Elicitation in the currently supported `2025-11-25` protocol revision. RepoPilot will not add support for the newer `2026-07-28` protocol in this slice. Form-mode clients must declare their Elicitation capability; the protocol requires a client UI that identifies the requesting server and lets the user decline or cancel. See the [2025-11-25 Elicitation specification](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation). A capability declaration or accepted response is still supplied by the MCP client: it is not cryptographic proof of a human action and does not protect against a malicious or compromised client.

## User-visible behavior

- A review without selected checks performs no consent exchange and behaves as it does today.
- For each selected check, in deterministic order, RepoPilot sends one form-mode Elicitation request with a 120-second response deadline. The form has one required boolean, `approve`; only `action: accept` with `approve: true` authorizes execution. The message identifies the check ID and displays the resolved program, exact argument vector, working directory, and the fact that the process has the host user's permissions and is not sandboxed. It does not include process output or environment values.
- An accepted response authorizes only that check in that `repopilot_review_change` call. RepoPilot does not cache or persist the decision.
- A declined check is skipped; remaining selected checks may still be offered. A cancelled or timed-out interaction stops further prompts. No declined, cancelled, unsupported, or invalid interaction starts a process.
- Before any accepted check starts, RepoPilot revalidates the effective configured check and the workspace revision captured for the review. Any mismatch invalidates the pending consent and skips the check.
- If the client did not negotiate form-mode Elicitation, selected checks are skipped without an Elicitation request. The ordinary static review result is still returned.
- A check that was not authorized is represented as skipped with a specific limitation such as `user declined`, `client does not support approval`, `approval timed out`, or `workspace changed before execution`. It must never be represented as passed or as verified.
- Elicitation transport failures must not corrupt the stdio JSON-RPC stream or turn the static review into an execution attempt.

## Security and privacy boundaries

- Consent applies to one resolved check and one MCP tool call; it does not grant future permission to the repository or check ID.
- The approval prompt includes command details so the user can assess what will run. Do not include environment values or process output. Repository owners should not place secrets in program or argument fields because those details pass through the MCP client.
- A successful confirmation does not sandbox the process. The selected program can still use the host user's available filesystem and network permissions.
- This design relies on the connected MCP client to display Elicitation honestly and obtain the user's choice. It does not defend against a client that fabricates an accepted response, a compromised host, or a user who approves malicious code.
- No check may run when consent is absent, stale, invalid, cancelled, or declined.

## Scope

Included:

- Store the negotiated client Elicitation capability needed by `tools/call`.
- Add the request/response path required for server-initiated Elicitation over the current stdio transport, with request IDs isolated from client requests, response validation, cancellation, and a bounded timeout.
- Gate selected verification checks on individual accepted responses.
- Revalidate the workspace revision and effective command definition before spawning an accepted check.
- Record skips with an explicit limitation and preserve the existing unverified semantics.
- Update MCP tool descriptions, security/MCP documentation, the v0.25 roadmap and evidence ledger, and `CHANGELOG.md`.
- Keep response ordering, progress notifications, cancellation, and ordinary tool calls deterministic.

Excluded:

- New analysis rules or changes to quiet-fallback semantics.
- Persistent approvals, a host allowlist, or a new configuration schema.
- OS sandboxing or claims that RepoPilot constrains a successfully approved process.
- MCP protocol `2026-07-28` support or broad client compatibility claims.
- Changes to CLI verification behavior.

## Acceptance criteria

1. An MCP `initialize` request that declares `elicitation.form` allows the server to request a form confirmation during an active review call.
2. An accepted Elicitation causes only the matching check to run, with the approved program, arguments, and working directory.
3. Decline, cancel, timeout, malformed response, unsupported protocol/capability, and workspace/config drift all cause zero process launches for the affected check.
4. The stdio loop routes a response only to its matching pending server request; unrelated or late responses cannot authorize a check.
5. With no `verify` IDs, no Elicitation request is emitted. With multiple IDs, checks are offered one at a time in deterministic order.
6. The MCP review still returns static findings when a check is skipped, states why it did not run, and never claims verification passed.
7. CLI `--verify` retains its current behavior.
8. Regression tests use a temporary sentinel executable to prove both that accepted checks launch and that every denial/stale-input path does not launch.
9. MCP protocol tests cover initialize negotiation, request/response routing, cancellation, timeout, malformed/unknown response IDs, and interleaved ordinary notifications without corrupting JSON-RPC output.
10. Documentation makes the client capability requirement, host-permission boundary, no-sandbox limitation, and lack of persistent consent explicit.

## Release evidence

Close the implementation ledger row only after focused tests, applicable full handoff gates, and a dogfood review pass. Record the merged commit and hosted CI. Test at least one real MCP client that advertises form Elicitation before claiming the interactive path is usable there. Other clients remain unverified unless separately observed.
