## Limits

- The synthetic and historical workloads exercise different paths; do not
  combine their timings into one speedup claim.
- Criterion's medium full-scan interval has one high outlier; report the range
  and median estimate rather than a false-precision point comparison.
- No release/package version, report schema, detector behavior, or user-facing
  compatibility claim is inferred from these measurements.

## Final matcher fast-path follow-up

The release-preparation gate also found that the JS/TS matcher recognizer
expanded every assertion's full expression before rejecting ordinary matchers
such as `toBe`. It now checks the AST property first and only expands the
expression for `toEqual` or `toMatchObject`; matcher semantics are unchanged.

Same-host comparison: Darwin arm64, Rust 1.94.0, Node 26.11.1, using the same
20-file integrity workload and `scripts/check-review-performance.js`.

| Scenario | Before fast path | After fast path | Change |
|---|---:|---:|---:|
| Integrity-phase median | 17.628 ms | 15.484 ms | -12.2% |
| Whole 20-file review median | 268.24 ms | 262.54 ms | -2.1% |
| Integrity share | 6.57% | 5.90% | -0.67 percentage points |

Both runs stay below the 1,000 ms absolute limit and the 10% share limit.
These figures describe one host; the hosted runner showed higher share
variation, so the gate remains enabled and its threshold is unchanged.

## Cross-file helper preflight follow-up

The hosted review fixture exposed a separate cost. A phase trace showed the
cross-file helper pass taking 8.9–10.5 ms out of a 12.1–14.9 ms integrity
phase. The pass built the full Git file inventory before checking whether a
changed JS/TS helper had assertion evidence. Ordinary test/source edits with
no changed assertion helper therefore paid for an unnecessary inventory.

The helper-evidence check now runs first and returns before inventory creation
when no assertion helper changed. Changes with assertion-bearing helpers still
build the same inventory and use the same caller-attribution path.

Same-host comparison: Darwin arm64, Rust 1.94.0, Node 26.11.1, using the same
20-file `scripts/review-performance-integrity.js` workload.

| Scenario | Before preflight | After preflight | Change |
|---|---:|---:|---:|
| Integrity-phase median | 13.532 ms | 6.805 ms | -49.7% |

The full `npm run review:performance` gate passed after this change: 20-file
integrity review at 4.341 ms / 196.59 ms (2.21%), 123-file review at
1,047.14 ms against 2,100 ms, and changed/full ratio 0.300 against 0.6. The
local before/after figures are one-host measurements; the gate threshold was
not changed. Hosted CI for this follow-up is pending.
