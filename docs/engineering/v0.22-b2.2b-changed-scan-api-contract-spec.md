# v0.22 B2.2b — Changed-Scan API Contract Parity

Status: complete

## Relationship to B2.2

B2.2 is delivered as two focused changes:

- B2.2a moved TypeScript/JavaScript symbol facts into the shared analysis core
  and persisted them through cold and warm parsed-cache paths.
- B2.2b consumes those facts in `scan --changed` and projects the existing
  `behavioral.removed-export-still-imported` evidence as a scan finding.

This specification covers B2.2b only. It preserves B2.1's conservative
language and resolver boundary while establishing an extensible API-contract
analysis seam for future language-specific detectors.

## Problem

`review` can prove that a changed TypeScript/JavaScript module removed a named
export while a surviving local caller still imports that name. `scan --changed`
already owns the same Git diff, current repository graph, and persisted symbol
facts, but does not run the detector. Developers and maintainers can therefore
receive different conclusions for the same change.

Calling the review detector directly from scan would produce output parity but
would reload and reparse current callers, bypassing the B2.2a cache. Building a
universal multilingual symbol model would avoid that duplication but would
prematurely force languages with different namespace and resolution semantics
into a JavaScript-shaped abstraction.

## Outcome

RepoPilot owns one canonical removed-export occurrence contract and one stable
detector ID:

`behavioral.removed-export-still-imported`

The TypeScript/JavaScript detector consumes facts through a narrow provider
boundary. Review and changed scan supply those facts from their native sources:

- review uses its revision-aware source cache;
- changed scan uses current `ParsedArtifact` and parsed-cache facts, parsing
  only the authoritative pre-change exporter source when required.

The same proven occurrence is projected as a definitely-sensitive
`ReviewSignal` and as a High-confidence, High-severity changed-scan `Finding`.
The two public record shapes remain distinct, but their detector ID, semantic
identity inputs, evidence location, limitations, and verification guidance do
not drift.

## Product Surface

B2.2b changes the existing `scan --changed` surface and every projection of
its canonical findings:

- console, Markdown, JSON, HTML, and SARIF scan output;
- priority and severity CI gates;
- GitHub Action scan artifacts;
- `repopilot_scan` MCP results;
- stored fallback through `repopilot_explain_finding`;
- AI context and receipts where they already consume scan findings.

It adds no command, flag, MCP tool, or `FindingCategory`. Full scans remain
snapshot analyses and do not emit a change-only contract finding without an
authoritative comparison revision.

## Decisions

### One canonical detector ID

Review signal kind and scan finding rule ID are both
`behavioral.removed-export-still-imported`. A scan-specific alias such as
`code-quality.removed-export-still-imported` is not introduced because it would
split configuration, suppression, documentation, metrics, and user learning
for the same proven defect.

The rule registry gains a focused `behavioral` group. The scan finding uses
the existing `CodeQuality` category because adding a public `Behavioral`
category would expand every renderer and compatibility contract without adding
new evidence.

### Extensible core without a universal symbol model

`analysis::api_contract` owns language-neutral orchestration concepts and the
canonical occurrence record. TypeScript/JavaScript semantics remain in a
language-specific detector that consumes `JavaScriptSymbolFacts`.

Future languages add sibling adapters or detectors only when RepoPilot can
model their export, namespace, and resolver semantics honestly. They may reuse
the occurrence and projection layers without pretending that JavaScript
`value`/`type` namespaces describe every language.

### Fact ownership

The detector does not read files, invoke Git, build graphs, create parsers, or
own a cache. Its provider supplies:

- pre-change facts for supported modified exporters;
- current facts for exporters and direct caller candidates;
- the current file inventory used by the resolver.

This keeps revision and cache policy in the adapters that already own them.

### Finding evidence

The primary finding evidence is the surviving caller import occurrence. Its
path, line span, and deterministic snippet identify the imported name, local
binding, module specifier, and resolved exporter. The description identifies
the changed exporter and removed symbol.

No `target_path` field is added to `Finding` in B2.2b. The exporter remains
machine-readable inside the canonical internal occurrence and deterministic
evidence snippet, avoiding a broad public schema change. A future general
cross-file-finding contract may expose related paths consistently across
multiple rules rather than adding a one-rule field.

## Architecture

### Canonical occurrence

Add an internal occurrence under `analysis::api_contract` with the evidence
needed by either projection:

```rust
pub(crate) struct RemovedExportOccurrence {
    pub exporter_path: PathBuf,
    pub importer_path: PathBuf,
    pub exported_name: String,
    pub local_name: String,
    pub symbol_kind: SymbolKind,
    pub module_specifier: String,
    pub line_start: usize,
    pub line_end: usize,
    pub byte_start: usize,
    pub byte_end: usize,
}
```

Ordering and equality include exporter, symbol, importer, line span, and exact
byte span. The existing B2.1 `RemovedExportSignal` becomes this shared record
or a type alias during migration; no duplicate occurrence model remains.

### TypeScript/JavaScript detector

Move export-delta and caller-confirmation logic out of the review subsystem
into a language-specific module beneath `analysis::api_contract`.

The detector preserves B2.1 behavior:

1. consider only modified `.ts`, `.tsx`, `.js`, and `.jsx` exporters;
2. compare direct pre-change and current exports by name and symbol kind;
3. withdraw a claim when a current named or wildcard re-export can still
   supply the symbol;
4. use the dependency graph only to enumerate direct caller candidates;
5. require a surviving direct named import in current facts;
6. require the current resolver and current file inventory to select the
   changed exporter;
7. emit one occurrence per exact caller import span;
8. sort and deduplicate by exact occurrence identity.

Default/namespace imports, path aliases, workspace packages, dynamic/CommonJS
forms, file renames, deleted exporters, unsupported languages, malformed ASTs,
and unresolved or ambiguous targets remain outside the claim.

### Fact provider boundary

The detector consumes a narrow provider rather than concrete review or scan
types. The exact Rust shape may use a trait or explicit callbacks, but it must
provide lazy, memoized access equivalent to:

```rust
current_facts(path) -> Option<JavaScriptSymbolFacts>
pre_change_facts(changed_exporter) -> Option<JavaScriptSymbolFacts>
current_file_inventory() -> Option<&HashSet<PathBuf>>
```

The provider returns owned or borrowed facts without exposing parser or cache
lifecycle to the detector. A missing result means the evidence is incomplete
and suppresses the claim.

### Review adapter

The review adapter keeps its selected `DiffTarget`, `ReviewSource` cache, and
target-matched file inventory. It maps the canonical occurrences into the
existing review tiering function.

Review signal kind, confidence tier, gating, `target_path`, stable signal ID,
feedback suppression, impact lookup, verification plan, MCP retention, and
MCP replay remain unchanged.

### Changed-scan adapter

The changed-scan adapter runs after current file analysis and repository
context are available, but before enrichment, rule configuration, aggregation,
risk scoring, and contract validation.

For current facts it resolves paths in this order:

1. changed-file `ParsedArtifact` facts from the current scan;
2. `ParsedFactsCache` lookup using the repository-context path-to-content-hash
   key and current language for unchanged caller candidates;
3. no fallback parse for a current file when compatible persisted facts are
   unavailable.

Implementation discovery showed that B2.2a persisted symbol facts by content
hash and language but did not persist the path-to-hash link needed to retrieve
an unchanged caller without rereading it. B2.2b therefore adds the deterministic
content hash to each repository-context node and bumps that cache schema. The
context cache owns path/revision identity; the parsed cache continues to own the
symbol payload, so facts are not duplicated.

For the pre-change exporter it uses the changed scan's selected Git target and
the existing revision-aware source loader. That source is parsed once and
memoized for the detector pass. B2.2b does not require old content to have been
present in a previous cache.

The current resolver inventory derives from the same changed-scan repository
context revision, not from graph edges. The graph remains a candidate index,
never the proof of a symbol reference.

### Scan finding projection

Each canonical occurrence becomes one `Finding` with:

- rule ID: `behavioral.removed-export-still-imported`;
- category: `CodeQuality`;
- severity: High;
- confidence: High;
- provenance source: AST;
- analysis scope: `GitDiff`;
- primary evidence: the surviving caller import occurrence;
- recommendation: restore the export or update the caller, then run the
  repository's declared type-check, build, or test command manually.

The finding's stable baseline ID continues to use the existing enrichment
pipeline. Exact report-local identity uses the existing occurrence key, whose
primary evidence contains caller path, exact line span, and a deterministic
snippet with exporter and binding details. Two aliases on one line and the same
symbol imported by two callers must remain distinct occurrences.

### Rule capability metadata

Register the detector as Preview lifecycle with `ChangeSet` scope and
`PerChangeSet` cache policy. Its declared facts include Git diff, parsed symbol
facts, imports/exports, dependency graph, and workspace inventory.

Add a `SymbolFacts` capability to `FactKind` or an equally explicit internal
requirement rather than describing the rule as generic parsed syntax. This
keeps future scheduling and diagnostics honest about why the detector can run.

## Data Flow

```text
Git changed scope
  -> supported modified exporters
  -> pre-change exporter source -> one AST -> JavaScriptSymbolFacts

current changed artifacts -----------------------+
warm parsed-cache facts for unchanged callers ---+-> fact provider
current graph + current file inventory -----------+
                                                   |
                                                   v
                         TS/JS removed-export detector
                                                   |
                                RemovedExportOccurrence[]
                                      /                    \
                                     v                      v
                           ReviewSignal projection    Finding projection
```

## Cache and Performance Contract

- Current changed files reuse their already-created `ParsedArtifact`.
- Unchanged caller candidates reuse parsed-cache schema v4 facts.
- A current caller is never reparsed merely to run this detector.
- Each authoritative pre-change exporter is parsed at most once per changed
  scan.
- The graph bounds work to direct importer candidates.
- The resolver inventory is built once per detector pass.
- No compiler, package manager, network call, clock, randomness, or repository
  command beyond the already-selected Git diff/source target is introduced.
- Repeated cold and warm runs produce identical ordered occurrences, findings,
  IDs, occurrence keys, severity, confidence, and decision results.

B2.2b does not bump parsed-cache schema because it consumes the complete B2.2a
payload without changing its shape. It does bump the repository-context cache
schema to persist the missing path-to-content-hash lookup key and invalidate
older context entries that cannot support warm contract analysis.

## Error and Uncertainty Handling

- Missing pre-change source, current artifact, parsed-cache entry, graph,
  current inventory, or resolver selection yields no finding.
- Malformed or error-bearing pre/current AST facts yield no finding.
- A cache miss is not interpreted as an empty module contract.
- A deleted exporter remains owned by unresolved/missing-module evidence.
- A renamed exporter remains unsupported until the diff model retains an
  authoritative old path.
- Re-export uncertainty continues to withdraw overconfident claims.
- Failures to load required Git source propagate only when the surrounding
  changed scan already treats them as runtime errors; unsupported evidence
  remains a bounded omission.
- An empty result means no supported break was proven, not that the change is
  type-correct.

## Testing Contract

### Shared detector tests

- removed value export with a surviving named import;
- removed type export and type/value namespace behavior;
- coordinated rename guard;
- named and wildcard re-export guards;
- default, namespace, path-alias, package, dynamic, and CommonJS guards;
- malformed pre exporter, current exporter, and caller guards;
- resolver target must equal the changed exporter;
- two same-line aliases retain distinct exact occurrences;
- deterministic ordering across exporters, symbols, and callers.

### Projection parity tests

- review and changed scan produce the same canonical occurrence set;
- review signal behavior and MCP replay stay unchanged;
- scan finding uses the canonical rule ID, High severity/confidence, caller
  evidence, Git-diff scope, and stable deterministic identity;
- priority/severity gates react to the new finding through existing logic;
- rule disable and severity override use the shared rule ID.

### Cold/warm changed-scan tests

- cold scan detects the finding and populates current symbol facts;
- warm scan detects the identical finding while reporting parsed-cache hits;
- warm caller facts are obtained without increasing the parse counter;
- missing or invalid parsed facts suppress the claim rather than triggering a
  fallback current-file parse;
- `--since <base>` uses the selected base source and current working tree;
- unrelated changed files and unchanged safe callers remain silent.

### Quality evidence

- add true-positive and near-identical false-positive rule fixtures;
- add or update generated rule reference documentation;
- measure default-visible zoo output and update snapshots/expectations when
  `.zoo/` is available;
- do not claim a measured zoo precision result when the zoo is unavailable.

## Scope

### In scope

- Canonical internal removed-export occurrence.
- Shared TS/JS fact-level detector with review and changed-scan adapters.
- Changed-scan finding projection under the canonical ID.
- Behavioral rule registry metadata and explicit symbol-fact capability.
- Cold/warm, parity, identity, configuration, output, and fixture coverage.
- Roadmap, changelog, rule reference, and engineering documentation updates.

### Out of scope

- Full-scan comparison without a Git base.
- Languages other than `.ts`, `.tsx`, `.js`, and `.jsx`.
- Universal multilingual symbol facts or cache records.
- Path aliases, package imports, default/namespace imports, deep re-export
  propagation, CommonJS, dynamic imports, file renames, or deleted exporters.
- Compiler, type-checker, build, or test execution.
- New commands, flags, MCP tools, finding categories, or public target-path
  fields.
- Automatic fixes or source edits.

## Acceptance Criteria

1. Review and `scan --changed` use one canonical detector ID and occurrence
   contract for supported removed-export evidence.
2. Existing B2.1 review JSON, gating, feedback, identity, target path, impact,
   MCP retention, and MCP replay remain unchanged.
3. A supported unsafe change emits one High-confidence, High-severity scan
   finding per exact surviving caller import occurrence.
4. Near-identical coordinated rename, re-export, unsupported import, malformed
   AST, wrong resolver target, renamed file, and deleted file cases emit none.
5. Cold and warm changed scans emit identical findings and exact occurrence
   identities.
6. Warm current callers reuse B2.2a facts without a new parser pass.
7. Missing compatible current facts suppress the finding instead of being
   treated as an empty contract or triggering an unbounded parse fallback.
8. Rule disable, severity override, baseline identity, risk scoring, output,
   receipts, and CI gates work through existing finding infrastructure.
9. No parsed-cache schema bump occurs unless the persisted payload changes.
10. Focused tests, fixture quality gates, formatting, Clippy, the full Rust
    suite, release contracts, zoo validation when available, and RepoPilot's
    self-scan pass before handoff.

## Follow-up Direction

After B2.2b is measured and stable, future API-contract detectors may add
language-specific fact payloads and adapters beneath `analysis::api_contract`.
Promotion should be evidence-driven: a language joins only when RepoPilot can
model its namespace, module resolution, and caller semantics without weakening
the trust boundary of existing detectors.
