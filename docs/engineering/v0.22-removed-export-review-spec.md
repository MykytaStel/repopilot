# v0.22 B2.1 — Removed Export Still Imported

Status: implemented

Implementation status: B2.1 is implemented for the bounded review-first
evidence described below. `scan --changed` parity remains deferred to B2.2.

## Problem

RepoPilot can now prove that an explicit local module target is missing, but it
cannot yet detect the next common broken-code case: the module still exists
while a named export was removed or renamed and a local caller still imports
the old name.

The current parsed artifact records exported names and module-level dependency
edges, but it does not retain imported symbol bindings. Comparing export lists
alone would therefore overstate breakage: an export can be removed safely when
no caller imports it, while the same symbol name can exist in unrelated modules.

## Outcome

Add a conservative, review-first B2.1 detector for TypeScript and JavaScript.
It emits a definitely-sensitive review signal only when RepoPilot proves all of
the following from local static evidence:

1. a changed module exported a named symbol before the change;
2. that named symbol is absent from the module after the change;
3. a post-change local caller still has a direct named import of that symbol;
4. the existing resolver binds that import specifier to the changed module.

The stable signal kind is:

`behavioral.removed-export-still-imported`

The signal describes a removed export that remains imported. It may mention a
possible rename when the same change adds another export, but it never claims a
rename without semantic evidence.

## Product Surface

B2.1 is available through the existing `review` command and every projection of
its canonical `ReviewSignal` records:

- console and Markdown review output;
- review JSON;
- review gating through `--fail-on-review definitely`;
- `repopilot_review_change`;
- `repopilot_explain_review_signal` using the retained signal ID.

B2.1 adds no command, MCP tool, finding category, scan rule, or report score.
Parity with `scan --changed` is explicitly deferred to B2.2.

The canonical review signal gains one additive optional field, `target_path`.
For B2.1, `path` remains the exact caller/import evidence location while
`target_path` identifies the changed exporter used for impact lookup. Existing
signals omit the field, so their JSON shape and behavior remain unchanged.
Rust consumers that construct the public `ReviewSignal` via a struct literal
must add `target_path` (normally `None`), so this additive Rust field is a source
compatibility change even though serialized JSON remains compatible.

## Supported Evidence Boundary

### Supported in B2.1

- Source modules and importers ending in `.ts`, `.tsx`, `.js`, or `.jsx`.
- Named exports declared directly in the changed module.
- Direct named imports such as:
  - `import { loadUser } from "./api.ts"`;
  - `import { loadUser as load } from "./api.ts"`.
- Type-only named imports when the matching type export is removed.
- Any named import form of a name the post-change module no longer supplies
  under either symbol kind, because such a name breaks the import however the
  caller spelled it.
- Explicit relative module specifiers whose existing resolver selects the
  changed module as its current target.
- Modified exporter files where both pre-change and post-change source can be
  loaded at the same repository path for the selected review target.
- Changed and unchanged direct callers. The coupling graph bounds the caller
  candidates; each candidate is then confirmed from its post-change AST.

### Limited, never stated as broken in B2.1

- Path aliases, workspace package imports, or root-absolute imports.
- Default imports and default exports.
- Namespace or wildcard imports.
- Re-exports and barrel-mediated symbol flow. A post-change
  `export { name } from "..."` is treated as still supplying that name, and a
  post-change `export * from "..."` withdraws every removal claim about the
  module, because the forwarded source is not analyzed.
- Exporter file renames. The current review diff model does not retain the old
  path needed to load authoritative pre-change source, so B2.1 does not guess.
- CommonJS destructuring, dynamic imports, computed property access, or runtime
  mutation of the module object.
- Unsupported source languages.
- Exporter files deleted entirely; the missing-module detector owns that case.
- Cases where pre-change source, post-change source, a parse tree, a coupling
  graph, or a resolver selection of the changed module is unavailable.

Limited cases are omitted from default-visible review signals. B2.1 does not
add one diagnostic per unsupported import. A future bounded aggregate diagnostic
may be added only if it provides actionable information without review noise.

## Architecture

### 1. Typed symbol facts

Add a focused TypeScript/JavaScript symbol extractor that consumes the existing
shared `ReviewSource` tree and produces deterministic internal facts:

- `ExportedSymbolFact`: exported name, kind (`value` or `type`), and source span;
- `ImportedSymbolFact`: imported name, local binding name, kind, module
  specifier, and source span.

Facts are sorted and deduplicated by exact evidence identity, including the
private AST byte span for imported specifiers. They remain
internal to the review analysis and do not expand `FileFacts`, `ScanSummary`, or
the public parsed-artifact schema in B2.1.

The extractor must use AST node kinds and fields. Text or regular-expression
fallbacks cannot create a definitely-sensitive signal.

### 2. Export delta

For each modified supported module:

1. load its pre-change and post-change `ReviewSource` using the selected
   `DiffTarget`;
2. extract named exports from both sides, plus the names the post-change side
   forwards through a sourced re-export;
3. stop when the post-change side carries `export * from "..."`, which can
   supply any name;
4. compute `removed = before - after` by exported name and symbol kind, then
   drop every name the post-change side forwards;
5. record separately which removed names the post-change side no longer
   supplies under either symbol kind;
6. stop when either side cannot be read or parsed.

A symbol moving from value export to type-only export, or the reverse, does not
satisfy a caller of the old kind and remains eligible for confirmation. A name
that disappeared under both kinds is matched against every named import form,
because no spelling of the import can resolve it.

### 3. Bounded caller confirmation

Use the existing coupling graph only to enumerate direct importer candidates of
the changed module. For each candidate:

1. load the candidate's post-change source from the working tree or selected
   head revision;
2. extract its direct named imports once;
3. inventory file names from that same working-tree or selected-head target and
   use the existing local resolver to confirm that the import specifier targets
   the changed module;
4. match the imported name against the removed export, using the type/value
   kind only when the name still exists under the other kind.

The graph is a candidate index, not proof. A stale or incomplete graph can cause
a bounded false negative, but it cannot create a signal because the AST import
and resolver target must independently confirm the relationship.

Only direct callers are inspected. Transitive dependents contribute to the
existing impact view but cannot prove that they reference the removed symbol.

### 4. Canonical review signal

Emit one signal per `(exporter path, exported symbol, importer path, import
span)` occurrence with:

- family: `behavioral`;
- tier: `definitely-sensitive`;
- confidence: `high`;
- path and line: the surviving import occurrence in the caller;
- target path: the changed exporter whose contract lost the symbol;
- headline: `removed export is still imported`;
- detail: removed symbol, exporter path, imported/local binding names, and
  whether it is a type-only import;
- provenance: AST plus Git-diff/repository-graph context;
- blast radius: existing importer reach for the changed exporter;
- verification plan: inspect the exporter delta, update the caller or restore
  the export, then run the repository's declared type-check/build/test command
  manually. RepoPilot does not execute that command in B2.1.

The stable signal identity includes kind, normalized exporter path, exported
name, normalized importer path, and import span. It must not collapse two
removed symbols in one caller or the same symbol imported by two callers.

## Data Flow

1. `review` loads the diff and runs the existing scan/repository graph path.
2. The shared review pass loads pre/post source for changed exporter candidates.
3. The symbol extractor computes direct named-export deltas.
4. The coupling graph returns bounded direct-importer candidates.
5. Post-change importer AST facts plus the existing resolver confirm exact
   surviving references.
6. Confirmed occurrences enter the canonical tiered review signal pipeline.
7. Existing rendering, gating, feedback, MCP retention, and explanation paths
   project the same signal record; MCP impact lookup uses `target_path` when it
   is present and otherwise preserves the existing `path` behavior.

## Determinism and Performance

- No network, command execution, clock, randomness, or compiler invocation.
- No second repository-wide content walk or graph reconstruction. The resolver
  may obtain one Git-backed file-name inventory for the selected review target.
- Parse each changed exporter side at most once within the review source cache.
- Parse each candidate caller at most once per review target and share its
  extracted symbol facts across all removed exports.
- Sort exporter paths, symbols, importer paths, and spans before signal creation.
- Bound work to supported changed exporters plus their direct graph importers.
- Extend review timing only within the existing review-signal stage; a new
  public timing field is unnecessary for B2.1.

## Error and Uncertainty Handling

- Missing source, invalid UTF-8, parse failure, absent graph capability, or a
  resolver selection other than the changed module yields no
  definitely-sensitive signal.
- An empty result means no supported surviving named import was proven. It does
  not mean the change is type-correct.
- If the post-change module no longer exists, B2.1 yields ownership to
  `architecture.unresolved-local-import` and emits no duplicate signal.
- Duplicate syntax nodes or overlapping export forms are deduplicated only by
  exact fact identity, never by symbol name alone.
- Existing review feedback suppression continues to operate on the stable
  signal kind and path without a new suppression mechanism.

## Testing Contract

### Extractor tests

- direct named value export/import;
- type-only export/import;
- binding rename (`loadUser as load`);
- comments and strings do not create facts;
- default, namespace, dynamic, and CommonJS forms remain unsupported;
- facts and spans are deterministic.

### Detector fixtures

- unsafe: removed named export with an unchanged direct caller;
- unsafe: removed type export with a surviving type-only caller;
- unsafe: removed type export with a caller that omits the `type` keyword;
- safe: export and all callers renamed together;
- safe: removed unused export;
- safe: same symbol imported from another module;
- safe: existing export with an unchanged caller;
- safe: implementation moved behind a sourced re-export of the same name;
- safe: post-change `export * from "..."` withdraws the claim;
- safe/limited: path alias, namespace import, re-export, and parse failure;
- safe ownership: deleted module produces no B2.1 duplicate.

### Integration contracts

- working-tree, `--base/--head`, and snapshot-style review targets agree for the
  same before/after repository state;
- JSON and console project the same signal occurrence;
- `repopilot_review_change` returns the canonical signal;
- `repopilot_explain_review_signal` replays it by stable ID with impact,
  verification, provenance, and limitations;
- two symbols in one caller and one symbol in two callers retain distinct IDs;
- review gating counts the unsuppressed signal as definitely-sensitive.

## Acceptance Criteria

1. Removing `export function loadUser()` while a local direct caller still has
   `import { loadUser } from "./api.ts"` produces exactly one High-confidence,
   definitely-sensitive review signal at the import line.
2. Renaming both the export and every caller in the same change produces no
   signal.
3. `import { loadUser as load }` still detects removal of `loadUser` and reports
   both the imported and local binding names.
4. A same-named export or import in another module cannot satisfy or trigger the
   relationship.
5. Unsupported resolution and symbol-flow forms produce no broken-code claim.
6. The signal ID is stable across repeated reviews of the same repository state
   and distinct across separate occurrences.
7. Review CLI, JSON, gating, MCP review, and MCP explanation agree on the same
   canonical signal.
8. Existing review verdicts and output remain unchanged when no supported
   removed-export relationship is proven.
9. Targeted tests, full Rust tests, formatting, clippy, release contracts, and
   RepoPilot self-scan pass before handoff.

## Deferred to B2.2 and Later

- `scan --changed` parity and persisted symbol-fact caching;
- path aliases and workspace packages;
- re-export/barrel symbol propagation;
- default and namespace import analysis;
- Rust, Python, Go, or compiler-backed symbol resolution;
- explicit verification execution, which belongs to Phase D.
