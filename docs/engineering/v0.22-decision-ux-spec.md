# v0.22 Decision UX Contract

Status: done

## Problem

RepoPilot's default profile can report `Health: 100/100` while also hiding a
large strict-only maintainability backlog. The value is internally consistent
because profile filtering recomputes health from visible findings, but the label
can be read as a claim about the whole repository. Review output has a related
hierarchy problem: its default `findings` detail prints every changed file before
the signals that need attention.

## Outcome

The scan surfaces two stable, honest product signals:

- `Visible health` measures only findings visible after the selected profile and
  explicit CLI filters.
- `Maintainability` measures findings hidden by the default visibility policy,
  regardless of whether the current output profile is `default` or `strict`.

Verdicts, CI gates, risk priority, baseline matching, and finding visibility
remain based on the existing visible finding set. Review's default console view
keeps the decision and signals prominent by bounding the changed-file inventory.

## Health Semantics

`ScanMetrics.health_score` remains the visible score for compatibility. A new
`maintainability_score: u8` is computed before profile filtering from findings
where `is_visible_by_default` is false, using the existing size-normalized health
formula. The same raw input must produce the same maintainability score in
default and strict profiles.

Human output labels the two values exactly:

- `Visible health: N/100`
- `Maintainability: N/100`

JSON exposes `health_score` unchanged and adds `maintainability_score`. This is
an additive report contract change, so the current report schema advances from
`0.23` to `0.24` while readers continue accepting the older supported versions.
SARIF finding and gate semantics do not change.

Workspace scans aggregate the two scores with the same LOC-weighted rule used
for the existing health score. Baseline, scan, Markdown, HTML, console, report
fixtures, and MCP scan output must project the same values.

## Review Progressive Disclosure

`DetailLevel::Summary` remains unchanged. `DetailLevel::Full` continues to show
the complete changed-file inventory, blast radius, impact paths, and full
evidence.

The default `DetailLevel::Findings` view:

1. prints deterministic counts by top-level area (`src`, `tests`, `docs`, and
   other discovered roots);
2. prints at most 12 changed-file rows in existing stable order;
3. prints `... N more changed file(s); rerun with --detail full` when truncated;
4. keeps review signals and in-diff findings after that bounded inventory;
5. ends with a `Next:` block that tells the user to inspect visible signals or
   findings and names `--detail full` when more evidence is available.

JSON and Markdown changed-file inventories remain complete. No changed file is
removed from analysis, ownership, blast radius, or impact computation.

## Scope

### In scope

- Dual scan health semantics and additive report field.
- Console, Markdown, HTML, JSON, baseline, workspace, MCP, and golden parity.
- Bounded default review inventory and concrete next-step copy.
- Documentation and changelog updates.

### Out of scope

- CLI colors, icons, animation, terminal layout redesign, or interactive TUI.
- Changes to finding severity, risk scoring, visibility classification, gates,
  baseline identity, or review detectors.
- Performance cache or HTML filtering changes from the other v0.22 slices.

## Acceptance Criteria

1. A default scan with only strict-hidden findings can report visible health 100
   while maintainability is below 100, and the labels make the distinction clear.
2. Default and strict profiles produce the same maintainability score from the
   same raw finding set.
3. Explicit severity, confidence, priority, and rule filters change visible
   health but not maintainability.
4. JSON schema `0.24` includes `maintainability_score`; supported older reports
   still parse.
5. Workspace, baseline, MCP, console, Markdown, and HTML projections agree.
6. The default review view prints at most 12 changed-file rows and a deterministic
   remainder line; full detail prints every file.
7. Review analysis, gates, JSON, Markdown, ownership, blast radius, and impact
   paths are byte-for-byte or structurally unchanged apart from intended copy.
8. Focused renderer/schema tests and the full RepoPilot handoff gate pass.
