# MCP verification consent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require one-time, check-specific MCP Elicitation consent before a configured verification check can execute, while preserving static review and CLI behavior.

**Architecture:** Keep the current stdio worker model and add a correlated response path for server-initiated Elicitation requests. Gate MCP-selected checks in the shared review-verification path, recording denied or stale checks as `skipped` with an explicit limitation; leave the CLI path ungated. Revalidate both the workspace revision and the complete effective check policy after consent and immediately before each accepted check executes.

**Tech Stack:** Rust 2024, standard-library threads/channels and synchronization, serde/serde_json, existing MCP stdio transport, verification policy and outcomes, Rust unit/integration tests.

**Spec:** [`docs/engineering/v0.25-mcp-verification-consent-design.md`](v0.25-mcp-verification-consent-design.md)

## Global Constraints

- One-time consent authorizes one resolved check within one `repopilot_review_change` call; do not persist or cache consent.
- Request form-mode Elicitation only when the client declares `elicitation.form` and the negotiated protocol supports it; otherwise skip selected checks.
- Use a 120-second response deadline. Only `action: accept` with `content.approve: true` authorizes execution.
- A decline may be followed by the next selected check. A user cancel or timeout stops later prompts; no denied, malformed, unsupported, or stale path launches the affected process.
- Show the check ID, resolved program, exact arguments, working directory, host-user permissions, and no-sandbox boundary. Never include environment values or process output. Warn that secrets in program/argument fields are sent to the MCP client.
- Revalidate the reviewed workspace revision and complete effective check policy after consent, immediately before each accepted check executes.
- Keep `VerificationStatus::Skipped` and its limitation field as the user-visible representation; never call a skipped check verified or passed.
- Preserve CLI `review --verify` behavior, deterministic check ordering, stdio JSON-RPC framing, progress, and cancellation. Do not add support for protocol `2026-07-28`.
- Add no dependencies and keep source files below the repository's approximately 300-line limit.

## Review Focus

- A response with a wrong, unknown, duplicate, or late server-request ID must never authorize the active check; pin in Task 2's real-client correlation test.
- A client that advertises Elicitation but declines, cancels, times out, returns malformed content, or sends a JSON-RPC error must not launch the sentinel process; pin each path in Task 2's MCP verification tests.
- Editing a workspace input or changing the effective configured command while consent is pending must invalidate that consent; pin both drift cases in Task 2's freshness tests.
- MCP request cancellation and interleaved notifications while a request waits for consent must keep the JSON-RPC stream valid and stop execution; pin in Task 2's real-client cancellation test.
- No selected checks and unsupported/missing capability must emit no Elicitation request; pin in Task 2's no-capability integration test.

- Modify: `src/verification/policy.rs` — re-export `ValidatedCheck` and `ValidatedProgram` from the new focused module and keep policy selection/validation there.
- Modify: `src/verification/executor.rs` and `src/verification/mod.rs` — expose the existing skipped-outcome constructor to the command crate without changing outcome semantics.
- Modify: `tests/mcp_verification.rs` and its focused modules under `tests/mcp_verification/`, `src/commands/mcp/tests.rs`, `src/commands/review_verification/tests.rs`, and tests under `src/verification/policy/check.rs`.

**Interfaces:**
- `VerificationApproval` has `Accepted`, `Skip { limitation, stop_following }`, and `ToolCallCancelled`; Elicitation `action: cancel` becomes a skipped outcome, while MCP `notifications/cancelled` keeps existing whole-call cancellation semantics. Existing CLI `run_selected_with_context` remains ungated.
- `EffectiveConfigSource` in `verification_consent.rs` records `Explicit(PathBuf)`, `Discovered(PathBuf)`, or `Defaults`; the reload closure reads that same source and calls `select_checks` for the single check ID.
- `run_selected_with_approval(..., reload_check: &mut dyn FnMut(&str) -> Result<ValidatedCheck, String>, approve: &mut dyn FnMut(&ValidatedCheck) -> VerificationApproval)` prompts in deterministic order, then compares workspace revision and `same_execution_policy` against the reloaded check before calling the cached runner for each accepted check. Progress retains the original selected-check index and total.
- `ValidatedCheck::approval_details()` returns only check ID, resolved executable, exact argument vector, and working-directory display. Bare executable names are resolved against the configured process `PATH` at validation time; unresolved names cannot receive MCP approval. Preserve the selected PATH candidate (including a symlink alias) for execution so dispatcher tools retain their `argv[0]`; hash the content through that path. `ValidatedCheck::same_execution_policy(&self, other: &Self)` compares the full policy and executable SHA-256 identity, including role, timeout/output limits, applicability paths, and cache behavior. The MCP-approved runner rechecks that identity before cache reuse and process launch.
- `verification::skipped_outcome(check, revision, limitation, revision_compatible)` reuses the executor's existing canonical `VerificationStatus::Skipped` outcome shape for command-side consent decisions.
- Elicitation is enabled only for negotiated `2025-11-25` plus client capability `elicitation.form`. The form requires boolean `approve`; only `action == "accept" && approve == true` returns `Accepted`.
- Skipped outcomes carry a concrete limitation (`client does not support approval`, `user declined`, `user cancelled`, `approval timed out`, `invalid approval response`, `workspace changed before execution`, or `check definition changed before execution`).
