# MCP verification consent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require one-time, check-specific MCP Elicitation consent before a configured verification check can execute, while preserving static review and CLI behavior.

**Architecture:** Keep the current stdio worker model and add a correlated response path for server-initiated Elicitation requests. Gate MCP-selected checks in the shared review-verification path, recording denied or stale checks as `skipped` with an explicit limitation; leave the CLI path ungated. Revalidate both the workspace revision and the complete effective check policy after consent and immediately before each accepted check executes.

**Tech Stack:** Rust 2024, standard-library threads/channels and synchronization, serde/serde_json, existing MCP stdio transport, verification policy and outcomes, Rust unit/integration tests.

**Spec:** [`docs/engineering/v0.25-mcp-verification-consent-design.md`](v0.25-mcp-verification-consent-design.md)

## Global Constraints

- One-time consent authorizes one resolved check within one `repopilot_review_change` call; do not persist or cache consent.
- Request form-mode Elicitation only when the client declares `elicitation.form` and the negotiated protocol supports it; otherwise skip selected checks.
- Use a 120-second response deadline. Only `action: accept` with `content.approve: true` authorizes execution.
- A decline may be followed by the next selected check. A user cancel or timeout stops later prompts; no denied, malformed, unsupported, or stale path launches the affected process.
- Show the check ID, resolved program, exact arguments, working directory, host-user permissions, and no-sandbox boundary. Never include environment values or process output.
- Revalidate the reviewed workspace revision and complete effective check policy after consent, immediately before each accepted check executes.
- Keep `VerificationStatus::Skipped` and its limitation field as the user-visible representation; never call a skipped check verified or passed.
- Preserve CLI `review --verify` behavior, deterministic check ordering, stdio JSON-RPC framing, progress, and cancellation. Do not add support for protocol `2026-07-28`.
- Add no dependencies and keep source files below the repository's approximately 300-line limit.

## Review Focus

- A response with a wrong, unknown, duplicate, or late server-request ID must never authorize the active check; pin in Task 1's broker correlation tests.
- A client that advertises Elicitation but declines, cancels, times out, returns malformed content, or sends a JSON-RPC error must not launch the sentinel process; pin each path in Task 2's MCP verification tests.
- Editing a workspace input or changing the effective configured command while consent is pending must invalidate that consent; pin both drift cases in Task 2's freshness tests.
- MCP request cancellation and interleaved notifications while a request waits for consent must keep the JSON-RPC stream valid and stop execution; pin in Task 1's broker tests and Task 3's interactive transport test.
- No selected checks and unsupported/missing capability must emit no Elicitation request; pin in Task 2's no-capability integration test.

### Task 1: Correlated Elicitation transport

**Files:**
- Create: `src/commands/mcp/transport.rs` — own the stdio read/dispatch loop moved from `mod.rs`, leaving `mod.rs` below the file-size limit.
- Create: `src/commands/mcp/elicitation.rs` — pending-request correlation, bounded wait, cancellation polling, and Elicitation response validation.
- Modify: `src/commands/mcp/mod.rs` — delegate its current stdio loop to `transport.rs` and retain public command entry points/state declarations.
- Modify: `src/commands/mcp/jsonrpc.rs` — parse incoming JSON-RPC requests and responses as distinct message variants.
- Modify: `src/commands/mcp/worker.rs` — send broker requests through the shared writer and pass the broker into the tool-call context.
- Test: `src/commands/mcp/jsonrpc.rs` unit tests; `src/commands/mcp/elicitation.rs` unit tests; `src/commands/mcp/tests.rs` transport tests.

**Interfaces:**
- `jsonrpc::IncomingMessage` is either `Request(Request)` or `Response(IncomingResponse)`; `IncomingResponse` carries a JSON-RPC ID plus either result or error.
- `ElicitationBroker::request_form(prompt, cancellation, writer)` returns `Accepted`, `Declined`, `UserCancelled`, `TimedOut`, or `Invalid`; its resolver completes only the pending request with the same generated server ID.
- Server-generated IDs use a distinct `repopilot/elicitation/<counter>` namespace and are registered before writing. Unknown and late responses are ignored; the 120-second production deadline is injectable in unit tests.
- The transport loop routes client responses to the broker and keeps handling cancellation notifications and ordinary requests while the worker waits.

### Task 2: Consent-gated MCP verification

**Files:**
- Modify: `src/commands/mcp/mod.rs` — retain client capability and negotiated protocol support from `initialize`.
- Modify: `src/commands/mcp/worker.rs` and `src/commands/mcp/tool_call.rs` — pass a per-call consent callback to review dispatch.
- Modify: `src/commands/mcp/review_change.rs` — pass the selected validated checks, config source, and per-call consent operation into review verification.
- Create: `src/commands/mcp/verification_consent.rs` — resolve the exact config source, reload a selected check, format the user prompt, and adapt broker decisions.
- Modify: `src/commands/mcp/review_change/definition.rs` — describe the per-check consent requirement in the MCP tool contract.
- Modify: `src/commands/review_verification.rs` — prompt, revalidate, execute or append `skipped` outcomes one check at a time; stop later prompts after user-cancel/timeout.
- Create: `src/verification/policy/check.rs` — move `ValidatedCheck` and its existing implementation out of the already oversized `policy.rs`, then add its safe approval description and full-policy comparison.
- Modify: `src/verification/policy.rs` — re-export `ValidatedCheck` and `ValidatedProgram` from the new focused module and keep policy selection/validation there.
- Modify: `src/verification/executor.rs` and `src/verification/mod.rs` — expose the existing skipped-outcome constructor to the command crate without changing outcome semantics.
- Modify: `tests/mcp_verification.rs`, `src/commands/mcp/tests.rs`, `src/commands/review_verification/tests.rs`, and tests under `src/verification/policy/check.rs`.

**Interfaces:**
- `VerificationApproval` has `Accepted`, `Skip { limitation, stop_following }`, and `ToolCallCancelled`; Elicitation `action: cancel` becomes a skipped outcome, while MCP `notifications/cancelled` keeps existing whole-call cancellation semantics. Existing CLI `run_selected_with_context` remains ungated.
- `EffectiveConfigSource` in `verification_consent.rs` records `Explicit(PathBuf)`, `Discovered(PathBuf)`, or `Defaults`; the reload closure reads that same source and calls `select_checks` for the single check ID.
- `run_selected_with_approval(..., reload_check: &mut dyn FnMut(&str) -> Result<ValidatedCheck, String>, approve: &mut dyn FnMut(&ValidatedCheck) -> VerificationApproval)` prompts in deterministic order, then compares workspace revision and `same_execution_policy` against the reloaded check before calling the cached runner for each accepted check. Progress retains the original selected-check index and total.
- `ValidatedCheck::approval_details()` returns only check ID, resolved program, argument vector, and working-directory display. `ValidatedCheck::same_execution_policy(&self, other: &Self)` compares the full policy, including role, timeout/output limits, applicability paths, and cache behavior, before launch.
- `verification::skipped_outcome(check, revision, limitation, revision_compatible)` reuses the executor's existing canonical `VerificationStatus::Skipped` outcome shape for command-side consent decisions.
- Elicitation is enabled only for negotiated `2025-11-25` plus client capability `elicitation.form`. The form requires boolean `approve`; only `action == "accept" && approve == true` returns `Accepted`.
- Skipped outcomes carry a concrete limitation (`client does not support approval`, `user declined`, `user cancelled`, `approval timed out`, `invalid approval response`, `workspace changed before execution`, or `check definition changed before execution`).

- [ ] **Step 1: Add failing review-verification tests.** Name the tests `accepted_check_executes_and_declined_check_is_skipped`, `decline_continues_but_user_cancel_stops`, and `workspace_or_policy_drift_after_acceptance_skips_check`. Use a temporary sentinel executable to prove only accepted checks start and policy drift prevents both launch and cache reuse.
- [ ] **Step 2: Add failing capability tests.** Cover only `2025-11-25` plus `elicitation.form`, and prove that no capability or another negotiated revision produces a disabled consent path. Test no-check selection and deterministic prompt ordering through the consent callback.
- [ ] **Step 3: Extract and extend `ValidatedCheck`.** Move its current definition and implementation from `policy.rs` to `policy/check.rs` without changing behavior, then add `approval_details()` and `same_execution_policy()` there. Keep `policy.rs` below the source-file limit and preserve the public re-export.
- [ ] **Step 4: Implement capability negotiation and check-specific approval text.** Enable form-mode only for `2025-11-25` with `elicitation.form`. The prompt displays resolved program, exact argv, working directory, and the host-permission/no-sandbox warning without environment values or output.
- [ ] **Step 5: Implement consent-aware execution and fail-closed revalidation.** After each acceptance, compare `WorkspaceRevision::capture` with the review revision, reload/reselect the effective check from the same config source, and compare its complete policy before invoking the cached runner. On mismatch append a skipped outcome and do not start or reuse that check. A decline permits the next prompt; user-cancel/timeout stops later prompts; MCP request cancellation keeps whole-call cancellation semantics.
- [ ] **Step 6: Run focused MCP, policy, and CLI verification tests.** Run: `cargo test --test mcp_verification`, `cargo test --bin repopilot commands::review_verification`, `cargo test --bin repopilot verification::policy`, and `cargo test --test verification_cli`; Expected: PASS, and CLI explicit verification still launches exactly as before.
- [ ] **Step 7: Commit the consent gate.** Run `git add src/commands/mcp src/commands/review_verification.rs src/verification tests/mcp_verification.rs && git commit -m "feat(mcp): require consent for verification checks"`.
