# RepoPilot 0.27.0 — audit baseline and disposition

Status: **closed for the 0.27.0 implementation**. This is the baseline audit;
the shipped scope and remaining evidence gaps are recorded at the end.

Audit date: 2026-11-10. Code/document baseline: `origin/main` at `04f1b5e9`.
This audit was prepared against `origin/main` at `04f1b5e9` and then applied in
the `feat/v0.27.0` worktree.
The audit is based on targeted source and documentation inspection, prior
evidence ledgers, and GitHub release/issue metadata. It is not a full code,
security, usability, or real-repository precision audit. No new tests, zoo
scans, benchmarks, or independent user observations were run for this draft.

## Product outcome

Make a review useful from the first command through a concrete resolution:
users can establish what was reviewed, understand the strongest evidence, run
appropriate checks explicitly, and tell what remains uncertain. Expand analysis
where real examples justify it, without confusing a heuristic with a proof.
Keep analysis local, deterministic, and compatible with existing CLI, report,
MCP and agent workflows. Extend existing commands, not the top-level CLI.

## Findings and evidence

1. **P1 — Release status is contradictory.** GitHub shows `v0.26.0` published
   as a stable release on 2026-11-02, but `docs/roadmap.md`,
   `docs/roadmap/v0.26.md`, and `docs/engineering/v0.26-evidence-ledger.md`
   still describe it as unpublished. The README already links its release
   notes as latest stable. Verify all distribution channels independently
   before recording channel-specific claims and correct the release records.
2. **P1 — First-use effectiveness is unmeasured.** RP25-U01 and RP26-E01
   remain open; scripted setup and CLI tests are not independent observations.
   The README reaches review quickly, but the user still has to discover how to
   select verification checks, choose a base, and interpret an unverified pass.
   This is an evidence gap and a usability hypothesis, not a proven failure.
3. **P1 — Real-client MCP approval is unverified.** RP25-T08 records fixture
   and hosted CI evidence but no observed compatible client. Approval depends
   on client protocol/capabilities; checks have host permissions and are not
   sandboxed. Test the actual request, denial, cancellation, stale workspace,
   and unsupported-client paths before claiming client support.
4. **P1 — Review quality in production is unknown.** RP25-E01 and RP26-E02
   remain open. In the 0.26 ledger a self-review reported an advisory removed
   authentication signal on cache I/O where inspection found no auth edit.
   Reproduce on current code before classifying or fixing; do not infer a
   current false-positive rate from this single historical example.
5. **P2 — Coverage is bounded more narrowly than headline language support.**
   The generated language table marks eight frontends as rule-aware, while
   Rust contract detection and C# taint support have explicit syntactic and
   flow limits in the 0.25 ledger. Other detected languages may only have
   generic analysis. Make relevant coverage and abstentions available in the
   user's actual review, without implying whole-language correctness.
6. **P2 — Performance budgets can miss regressions.** RP25-T03 documents a
   roughly 60% local regression that stayed below the absolute hosted limit;
   RP26-05 documents a separate integrity-share limit failure. Existing
   optimizations and passing measurements are workload-specific. Compare
   matched baseline and candidate with full semantic parity, in addition to
   existing absolute budgets.
7. **P2 — Distribution and documentation need a single reliable journey.**
   Installation, first review, suggestions, verification, agent guardrails,
   MCP, and CI live across README and separate guides. Their existence does
   not establish that someone can navigate them unaided. Audit examples and
   links against released binaries and actual clients.

## Proposed release slices at audit time

Each slice should become a small independently reviewable PR, with an owner,
baseline, test evidence and a ledger row. Suggested priorities are proposals.
The release is intended to ship the product behavior below; research, tests,
and documentation support that behavior and do not replace it.

### Concrete product backlog

The examples below describe proposed behavior, not commands or features that
already exist. Final option names and schemas belong in the slice specs.

| Priority | Product change | User-visible behavior and boundary | Likely ownership |
|---|---|---|---|
| P1 | **Review check planner** | A review lists configured checks applicable to the changed paths, explains why each is suggested or unavailable, and offers a copyable rerun selecting explicit IDs. No check runs without explicit selection; MCP retains per-check consent. Previously `--verify` selected IDs are preserved in the suggested rerun. | `src/commands/review_verification/`, `src/review/decision/`, `src/cli/options/review.rs` |
| P1 | **Explain a review item from the CLI** | Add an entry point under the existing `review` command that expands one retained signal or finding: changed lines, evidence, confidence, impact, gate state, limitations and focused verification. Require an occurrence locator when an ID is ambiguous. Reuse existing MCP explanation semantics instead of inventing a new top-level command. | `src/review/`, `src/commands/mcp/explain_review_signal.rs`, `src/commands/mcp/explain_finding.rs` |
| P1 | **Review coverage breakdown** | Show analyzed, skipped, unsupported and failed portions when those facts are available, with specific reasons and recovery steps. Report unknown where attribution cannot be established. Make the same underlying facts available to agents and avoid treating an empty result as proof of safety. | `src/scan/`, `src/review/`, `src/output/`, `src/commands/mcp/` |
| P1 | **Fix misleading auth-removal signals** | Reproduce the documented cache-I/O example on the current baseline; if it still fires, narrow the recognizer to evidence of a real supported authorization boundary. Preserve meaningful auth-removal findings and expose uncertain cases as advisory. This is a targeted correction, not a general suppression of security findings. | `src/review/signals/`, relevant language frontends |
| P1 | **Actionable first-run setup** | Improve `init` and review recovery so a user can select a branch or dirty-tree workflow, see exactly which configuration is active, and resolve missing refs or checks with executable, correctly quoted instructions. Keep suggested checks separate from active configuration. | `src/commands/init/`, `src/cli/options/`, `src/commands/review/` |
| P2 | **Review change comparison** | Add a bounded comparison within existing review/report workflows that matches the same signal occurrences between two explicitly selected revisions or stored reports and shows introduced, resolved and unchanged items. Preserve exact occurrence identity and disclose unmatched or incomparable scope; never deduplicate on stable finding ID alone. | `src/review/`, `src/baseline/`, `src/output/` |
| P2 | **Useful impact paths** | Enhance blast-radius output with a short deterministic import path from a changed file to an affected entry point or direct consumer, when the graph can establish one. Label unresolved and ambiguous edges; cap expansion and avoid claiming runtime reachability. | `src/graph/`, `src/review/`, `src/output/` |
| P2 | **Multi-language analysis expansion** | Implement a bounded Rust public-API contract extension, for example a precisely resolved direct caller of a removed public struct field, if real examples and safe controls support it. Cover coordinated caller edits, unresolved aliases, macros and conditional compilation conservatively; otherwise choose another evidenced blind spot and record why. | `src/languages/rust/`, `src/review/signals/`, `src/rules/` |
| P2 | **Agent review continuation** | Extend existing MCP review flow so a client can discover omitted signals and request the next bounded page, preserving the same analysis handle and reporting stale handles. Existing finding pagination and explain tools already exist; build on them rather than presenting them as new. Preserve response limits and deterministic ordering. | `src/commands/mcp/review_projection.rs`, `src/commands/mcp/review_change/`, `src/commands/mcp/publication.rs` |
| P2 | **Resilient verification results** | Improve the existing check runner's status and recovery for missing executables, timeouts, cancelled checks and changed inputs; show the affected check and a safe rerun path. Keep timeout process-tree cleanup and distinguish skipped/failed/stale from passed. | `src/commands/review_verification/`, `src/review/decision/` |

Each candidate requires a short design against current `origin/main` before
implementation: verify the proposed capability is not already present, choose
its exact CLI/MCP interface, and assess schema compatibility. Order the work
into focused PRs; the P1 improvements and the multi-language analysis increments in RP27-05 form the proposed minimum product slice. Additional P2 work
is included only if it can be delivered and verified without weakening the
release gates. Evidence targets must be visible, but lack of independent users
must not silently turn this product roadmap into a documentation-only release.

### RP27-01 — Restore release truth and establish baseline (P1)

Reconcile 0.26 status, tag/commit and channel publication evidence; update the
roadmap and ledger without rewriting history. Capture exact 0.26 and current
baseline versions, supported platforms, schema, and representative CLI/MCP
outputs. Audit install and upgrade instructions against actual channels.
Acceptance: no contradictory stable-release status; every channel claim links
to verifiable evidence, and missing evidence remains explicitly open.

### RP27-02 — Guided review and verification journey (P1, major feature)

Design an end-to-end path within `init`/`review`: distinguish dirty working
tree, branch and snapshot reviews; show chosen scope and its limits; guide
selection of existing check IDs and the exact rerun; explain verified,
unverified, failed, skipped and stale states. Suggestions remain separate
from active configuration, and no generated command executes automatically.
Acceptance: runnable examples for each scenario, including missing base,
invalid config, no checks and cancelled checks; parity of decision and action
across console, Markdown, HTML, JSON and MCP where applicable; tests for
paths with spaces and deterministic output. Document actionable recovery.

### RP27-03 — Investigable evidence and coverage (P1, major feature)

Extend existing review/explain surfaces so a user can move from decision to
specific signal, source locations, confidence/provenance, affected scope,
limitations and a focused next step. Surface meaningful omissions such as
unsupported resolution or parse failures where actually known; do not present
an absent finding as a clean security result. Specify bounded output and a
stable machine-readable contract before implementation.
Acceptance: representative changed-code, partial-analysis and no-finding
cases produce consistent explanations in CLI and MCP; deterministic replay
and response-size limits are tested; additive schema changes are checked
against supported old readers and explicitly versioned if required.

### RP27-04 — Measured review precision and recall (P1)

Collect and label reproducible real change examples with selection criteria,
denominators, safe controls and missed cases; start with auth-removal noise,
error handling and weakened tests. Reproduce each candidate on the current
baseline before changing its rule. Correct evidenced false positives while
keeping strict recall and adding false-negative guards. Use the zoo snapshot
and reviewed expectation workflow when scan visibility changes; use sampled
strict labels for strict-only rules.
Acceptance: every changed rule has before/after examples, regression tests and
an explicit measurement scope; changed/cache/MCP paths have parity tests when
affected. No broad accuracy claim from synthetic fixtures or selected cases.

### RP27-05 — Expand analysis across supported languages (P1, major feature)

Ship several substantive language-analysis increments. The table distinguishes
documented boundaries from candidates that need reproduction against current
code. These are implementation targets, not claims that functionality shipped.

| Language | Proposed functionality and motivating example | Safe boundary and controls |
|---|---|---|
| Rust | Detect a removed public struct field with a uniquely resolved local field access or struct literal; extend existing function contracts to grouped imports and bounded sibling module paths. The 0.25 ledger explicitly excludes fields, grouped imports and sibling hierarchy. | Show declaration and affected use; coordinated edits, private fields, ambiguous symbols, macros and conditional compilation must not be asserted as proven breakage. |
| JS/TS | Resolve extensionless relative imports when one supported file or index target is established, then detect removed targets or broken direct exports. Evaluate uniquely resolved `tsconfig` aliases separately. The current unresolved-import rule excludes extensionless paths and aliases. | Respect actual resolution precedence; ambiguous candidates, package exports, dynamic imports and external modules require abstention or a limitation. |
| Python | Resolve repository-rooted absolute imports, including package `__init__.py`, and detect a removed local module or direct symbol. The current unresolved-import rule supports explicit relative modules. | Namespace packages, environment paths, installed dependencies, dynamic and optional imports remain uncertain unless resolved by an explicit model. |
| Go | Resolve module-local imports through uniquely identified local modules in `go.work` or local `replace` directives. Workspace packages and `replace` are current documented limitations. | Never fetch dependencies; remote replacements, missing members, build tags and generated code cannot become definite missing-package claims without sufficient evidence. |
| C# | Follow existing `CommandText` SQL flow across a simple local receiver alias, then across a bounded `if` merge when assignments and reachable paths can be modeled. Current analysis excludes aliases and invalidates state at branches. | Preserve receiver identity, clean overwrites and parameterized-query controls; ambiguous aliases, loops, fields and unknown calls require conservative handling. |
| Java and Kotlin | Add same-package type-reference edges for uniquely resolved source files, allowing impact analysis to find local consumers without imports. The unused-file rule currently excludes these languages because such references are invisible to the import graph. | Treat duplicate names, nested types, generated code, source roots and build variants conservatively; an edge does not prove runtime reachability. |
| Go, Python, JS/TS, Java and Kotlin | Audit HTTP-input to SQL, process and filesystem flows against real changes; implement reproduced missing sources, propagation or sinks for selected frontends. Confirm each gap first; frontend tables alone do not establish one. | Model supported local flow; distinguish SQL parameters, safe argument vectors and clean overwrites from unsafe construction. Generic escaping is not a universal sanitizer. |
| C/C++, Swift, PHP and other detected languages | Inventory high-value gaps and, if capacity allows, pilot bounded C/C++ file-backed local include edges. Generic analysis is not a full frontend. | Treat macros, compilation flags, generated headers and platform paths as uncertain; do not claim compiler equivalence. |

**Delivery commitment:** implement the Rust, JS/TS, Python, Go, C#, and
Java/Kotlin increments as independently scoped changes where their preconditions
can be established. Prioritize Rust contracts, JS/TS and Python resolution, Go
workspaces and C# flow; Java/Kotlin graph work follows. If a candidate already
exists or cannot be implemented soundly within its boundary, record the
explanation and substitute another reproduced gap in that language. Taint and
additional-language work are stretch targets.

Each increment needs a bounded design, real examples, unsafe and safe controls,
exact evidence, deterministic behavior and applicable full/changed scan,
cold/warm cache, CLI and MCP parity. Record performance and measured real-case
results with denominators. Invalidate caches and preserve report compatibility
when new parsed facts or evidence require it.

### RP27-06 — Agent and CI integration reliability (P1)

Exercise MCP setup and selected-check consent in actual available clients;
test denial, timeout, cancellation, changed policy/workspace, unsupported
elicitation and server restart. Check agent snapshot/hook and GitHub Action
instructions on pinned versions, including recovery and upgrade. Preserve the
explicit host-permissions/no-sandbox boundary and never call skipped work
verified. Record unavailable client/platform combinations as untested.
Acceptance: a versioned client matrix with observed evidence, automated
protocol regressions, documented recovery and no unsafe automatic execution.

### RP27-07 — Predictable scale and cache correctness (P2)

Add paired same-host candidate/baseline checks for representative small,
large, dirty, branch and warm/cold workloads; track median, variability, peak
memory and complete semantic-output parity. Investigate regressions with
phase timing rather than widening limits. Exercise config creation, edits and
deletion in a long-lived MCP process and cache invalidation.
Acceptance: reproducible environment and workloads, repeated measurements,
recorded variance and thresholds, plus targeted parity tests; report results
as workload-specific rather than a universal speed claim.

### RP27-08 — Documentation and adoption validation (P1)

Create a task-oriented short path for individual review, team/CI use and each
supported agent, with copyable commands and real output interpretation. Include
installation, base selection, verification consent, suppressions, limitations,
updates and troubleshooting. Run maintainer walkthroughs and seek independent
first-use observations; record who/what was observed without personal details.
Acceptance: examples exercised against the release candidate; broken links and
contradictions fixed; independent evidence remains open if unavailable. Do not
represent scripted walkthroughs as user research.

## Release checks and sequencing

1. Resolve RP27-01 and define the release contract and evidence ledger on a
   fresh branch from current `origin/main`.
2. Establish real-case baselines and journey tests; draft bounded specs for
   RP27-02, RP27-03 and the selected RP27-05 capability.
3. Implement and review slices independently; keep docs and ledger current.
4. Run focused positive/negative and integration tests throughout; before
   handoff run formatting, Clippy, full tests, release contract, applicable zoo
   expectations, performance and platform checks, and release dogfood.
5. Verify release-channel and client evidence separately; report untested
   combinations and residual issues. Prepare release only after acceptance.

Release gates must preserve deterministic local analysis, schema compatibility,
user consent for MCP-selected checks, and honest coverage. Independent user
testing and real-world precision are evidence objectives, not facts implied by
passing CI. If unavailable, the owner must decide whether to accept the open
evidence gap; do not silently mark it complete.

## Decisions before implementation

- Confirm the breadth and order of the major feature slices and their release
  trade-offs; a single release need not claim every proposed capability.
- Confirm the proposed per-language boundaries against real examples and current code.
- Decide which real clients and independent participants are available; avoid
  claiming coverage for unavailable platforms or unobserved workflows.
