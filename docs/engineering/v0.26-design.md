# RepoPilot 0.26 — balanced usability, signal quality, and performance

Status: approved, implementation in progress

Target: v0.26

Base: `origin/main` at `6537ccf1` (includes merged PR #609)

Related scope: `docs/roadmap.md`, `docs/roadmap/v0.25.md`,
`docs/engineering/performance-budgets.md`

## Decision

Build the 0.26 release around three connected outcomes:

1. Make the path from an unfamiliar checkout to a useful first review clearer.
2. Improve the precision and actionability of existing review signals without
   adding detector families.
3. Reduce measured latency and resource use without changing review meaning.

This is the balanced scope selected by the project owner. The owner has also
directed that work proceed without external testers or independent
observations. The first-use and labeled-production-evidence rows remain open;
the release must not present local fixtures or maintainer-run checks as
independent user or accuracy evidence. This owner-directed 0.26 scope may
proceed while those rows remain open.

## Current state

RepoPilot 0.25.0 is the latest package release. PR #609 and the other recent
0.25 work are already merged into `main`; they are not work to append to an
open PR. The JSON report schema is currently `0.26`, which is independent of
the package version. This release must keep those two version numbers
distinct.

The product already has `init`, `review`, `scan`, decision summaries, proof
cards, recommendations, hidden-suggestion explanations, local feedback, and
multiple report formats. The first-use path runs through `init`, optional
suggestion review, and `review`; 0.26 should make the next step clearer within
that existing command surface instead of duplicating it with another
diagnostic command. Source inspection found that `init --path` prints
`repopilot review .` without the custom `--config` path, even though its scan
suggestion does include it. The default console review also renders the
canonical `Next action` first and a second generic `Next` block after the
findings. `init` also exports detected verification suggestions without
comparing their IDs with the active config, leaving users to remove duplicates
by hand. Existing performance budgets cover scans, a pinned 123-file review,
and a 20-file integrity review. The documented small synthetic case measures
warm changed-review at about 124 ms versus about 90 ms cold because cache
loading/lookup can cost more than reparsing at that scale. Peak-memory
measurement is documented, but there is no pinned hard memory budget.

## Goals

- Help a user move from setup to the first useful review through the existing
  commands, with clear coverage limits and a concrete next command.
- Make existing findings easier to triage by preserving proof, coverage,
  confidence, suppression, and remediation boundaries in every presentation.
- Remove or correct existing signal behavior only when a concrete repository
  fixture or already documented defect demonstrates the problem.
- Profile representative CLI, review, scan, and cache paths before optimizing;
  record comparable before-and-after latency and resource measurements.
- Keep local execution, deterministic findings, and current privacy boundaries.
- Ship the work as a cohesive 0.26 milestone, with changes divided into
  reviewable implementation slices and one release contract.

## Non-goals

- No new detector families, language expansion, or broader syntax coverage.
- No claims of production precision/recall, independent usefulness, adoption,
  or first-use success from maintainer-run fixtures or benchmarks.
- No execution of configured checks as part of setup guidance.
- Do not change `init`'s explicit file-write/`--force` behavior or edit external
  clients as a side effect of guidance.
- No breaking CLI, MCP, JSON, SARIF, or report-schema changes in this release
  slice. Additive output changes need an explicit compatibility decision.
- No broad rewrite of the analysis engine or new hard memory budget without a
  stable, pinned baseline.

## Design choices

### 1. Balanced release — selected

Pair first-run clarity with signal presentation/correction and measured
performance work. Each area has a concrete user outcome, while existing report
and analysis contracts remain the compatibility boundary.

### 2. Detector expansion

Add more rule families and syntax coverage. This could increase headline
coverage, but it would introduce unmeasured signals and dilute the current
focus. It is deferred; 0.26 will not add detector families.

### 3. Performance-only release

Concentrate on engine speed and memory. This leaves the first-use friction and
signal actionability untouched, so it is not the selected direction.

## Workstreams

### A. First-use guidance in existing commands

Improve the path through `repopilot init`, `repopilot review`, and the setup
documentation. Do not add or restore a `doctor` command. The project removed
`doctor` in PR #186 because it diagnosed a setup surface with little value for
a single static binary, while `scan` and `review` already reported their
errors clearly. The 0.26 scope must honor that product decision and solve only
concrete friction in the commands that remain.

Keep one short install-to-review route and make each step say what it does:

- `init` creates only the files explicitly requested and points to the next
  useful command without implying that a scan or verification has run;
- when `init --path` writes a non-default config, its suggested first review
  uses that same config path;
- label the two existing `init` follow-up commands by intent: review the
  current change, or scan the whole repository;
- omit already configured verification IDs from the exported suggestions and
  show which IDs were omitted in console guidance;
- if the active config cannot be read or parsed, keep `init` usable, include
  all suggestions, and disclose that duplicate comparison was unavailable;
- suggestion output remains reviewable and separate from active configuration;
- `review` explains the actual empty-change, missing-base, invalid-config, or
  incomplete-verification state and gives a safe, state-specific next command;
- no default base, verification ID, or integration setup is silently chosen.

Before changing copy or output, compare the current behavior with these states
and change only a gap that is present. Guidance must not run configured checks,
install dependencies, access the network, change Git state, or edit external
clients. Keep the existing `init` write and `--force` contract. Keep the initial
interface text-first; machine-readable output is deferred until a stable
consumer contract is justified.

### B. Existing-signal quality and report actionability

Keep the current detector inventory and signal identifiers. Review the
existing-signal path from evidence to the user's next action:

- ensure the most important finding/proof action is visible before secondary
  detail in console, Markdown, and HTML;
- keep one canonical primary action in the console report; a secondary detail
  hint may point to `--detail full`, but must not read like a competing action;
- make confidence, evidence limits, hidden suggestions, and suppression state
  clear where they affect the decision;
- avoid repeating the same occurrence as multiple equally prominent actions
  when existing identity/provenance already shows they are duplicates;
- correct a signal's behavior only when a concrete existing fixture or
  documented defect supplies both a failing case and a legitimate safe
  control;
- preserve the current non-gating/advisory boundary for signals whose syntax
  does not prove harmful behavior.

This work improves consistency and triage, not claimed real-world accuracy.
Do not lower thresholds, raise confidence, broaden matching, or change gate
eligibility to make reports look cleaner. If the source and fixtures do not
show a concrete signal defect, leave its detection semantics unchanged and
record the candidate for later evidence.

### C. Profile-led performance and resource use

Establish same-host before/after measurements for the existing pinned paths:

- 123-file historical review (current median budget: 2,100 ms);
- 20-file integrity review (current median budget: 1,000 ms; integrity work at
  most 10% of review median);
- representative cold/warm full and changed scans across the existing
  synthetic size matrix;
- startup and first useful review, including updated first-use guidance;
- peak RSS for at least the large scan and large changed-review workloads.

Profile before editing hot paths. Optimize only a measured dominant cost.
Specifically profile the small changed-review cache load/lookup and write path;
the existing benchmark note is a candidate to improve, not permission to
trade away larger-repository cache benefits.
Report workload, host/toolchain, warm/cold state, sample method, latency,
memory, and normalized semantic output. Preserve deterministic results,
cache parity, changed/full scope differences, evidence locations, and existing
performance ceilings. Do not set a hard memory budget until repeatable pinned
baseline data supports one. Any existing-budget change needs a documented
reason and the same before/after method.

## Compatibility and safety contract

- Existing CLI options, exit codes, MCP tools, signal IDs, and report meanings
  remain compatible.
- Setup guidance does not imply that checks passed or that a review is
  verified.
- `PASS (not verified)`, `VERIFIED`, `REVIEW`, `BLOCK`, and `NOT ASSESSED` keep
  their current distinctions.
- Human-readable output may become more concise, but JSON/SARIF/MCP evidence
  and suppression semantics stay aligned with the canonical decision.
- Any finding correction preserves unsafe and safe examples and explicitly
  retains abstention for unsupported or ambiguous cases.
- No change claims independent observation, real-user usefulness, or
  production detector accuracy. The relevant roadmap evidence rows stay open.

## Acceptance criteria

1. In fresh, existing, invalid-config, dirty, and no-reviewable-diff states,
   the existing setup/review commands give an accurate status and safe next
   step. A custom `init --path` is preserved in the printed first-review
   command. No new readiness subcommand is added, and guidance launches no
   configured process.
2. Setup guidance clearly separates setup suggestions, review coverage, and
   explicit verification. For a readable config, the generated TOML omits
   already configured check IDs and console output names them; for an
   unreadable/invalid config, all candidates remain visible with a note that
   duplicate comparison was unavailable. The docs give one short
   install-to-review route and explain its limits.
3. Console, Markdown, and HTML present the same canonical decision and one
   useful primary next action. Console's secondary detail hint is clearly
   labeled as such. JSON, SARIF, MCP, gates, and signal semantics stay
   compatible unless a separately approved additive contract is needed.
4. Existing-signal changes are limited to concrete defects supported by a
   failing fixture and legitimate safe control. No detector family or
   confidence/gating expansion ships in 0.26.
5. Performance work records reproducible before/after measurements on the
   applicable pinned workloads, does not exceed existing ceilings, and
   preserves normalized semantic output and deterministic cache behavior.
6. The release ledger clearly separates locally verified behavior from the
   still-open independent first-use and production-evidence work.
7. Release notes describe user-visible changes, measured performance deltas,
   compatibility, and remaining limits without implying uncollected evidence.

## Delivery sequence

1. Update the roadmap for the owner-directed 0.26 scope while leaving
   independent first-use and production-evidence rows open.
2. Improve the existing `init`/`review` first-use guidance where the state
   review identifies a concrete gap; update command/setup documentation.
3. Implement report actionability and any individually justified corrections
   to existing signals; keep detector semantics unchanged where evidence is
   insufficient.
4. Profile the complete changed paths, optimize the measured bottlenecks, and
   record comparable performance/resource evidence.
5. Complete the 0.26 release contract, changelog, release notes, and
   distribution evidence before proposing the release.

Package version remains 0.25.0 during implementation. The approved workstreams
are being tracked in their implementation plans; a release-version change is
reserved for the final release-preparation slice.
