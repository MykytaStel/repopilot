# Phase B: Review Setup Path for Unconfigured Verification

Status: done

## Problem

When a review cannot verify required checks, the first screen can recommend
installing or configuring checks without showing a short, reviewable path from
the current repository to a verified review. First-time maintainers must infer
how to use `init` suggestions, add accepted checks to the active config, and
rerun review with verification enabled. An already configured but unavailable
check needs repair guidance, not another copy of the same config entry.

## Outcome

A developer can follow a concise next action that matches the verification
state: add only missing accepted suggestions when policy is absent, or repair
an existing unavailable check. The user reruns the same review command with
its original path, revision, scope, and config arguments, including the
accepted `--verify <check-id>`. The flow preserves RepoPilot's local-first,
no-implicit-action behavior.

## Scope

- Update the shared review next action for a missing proof policy, a missing
  matching check, and an existing unavailable check. The setup path shows the
  concrete command `repopilot init --suggestions-output .repopilot/init-suggestions.toml`, tells users to review suggestions and add
  only missing accepted entries to active config, then rerun the same review
  with `--verify <check-id>` while preserving its original arguments. For an
  already configured unavailable check, explain that it needs repair and the
  original review should be rerun with its configured ID.
- Keep the action concise enough for the first screen and consistent across
  console, Markdown, HTML, JSON, SARIF, MCP, and Action projections that share
  the review decision.
- Add a short `docs/configuration.md` walkthrough from an initial review to a
  successful verified review, designed to take under five minutes.
- Add regression coverage for the two setup cases and retain the precedence of
  failed checks and high-priority human-review evidence over setup guidance.

## Non-goals

- Do not run suggested commands, install dependencies, or change the active
  configuration automatically.
- Do not change verification policy semantics, verdict derivation, or the
  priority of review findings and sensitive signals.
- Do not add a CLI command or implement new stack detectors.

## Acceptance Criteria

1. Reviews with no matching configured check and reviews without a sufficient
   proof policy point to the same explicit suggestions-file workflow; an
   existing configured unavailable check points to repair guidance.
2. The generated file remains separate from active config; only reviewed,
   missing entries are added as active checks.
3. The documented sequence reruns the same review command, preserving its
   original path, revision, scope, and config arguments while using
   `--verify <accepted-check-id>`; the review remains unverified until a
   selected required check actually passes.
4. Existing higher-priority next actions for failed checks and high-priority
   evidence are unchanged.
5. Tests cover the next-action text and shared projection behavior; the docs
   walkthrough is runnable in a local Rust or Node.js repository.

## Verification Plan

- Run focused next-action and first-screen/projection parity tests.
- Run the RepoPilot local pre-handoff gate after implementation.
- Dogfood `cargo run --release -- review . --base origin/main` and confirm the
  first screen offers the setup path only when appropriate.
