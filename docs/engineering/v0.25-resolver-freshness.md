# Resolver freshness evidence (RP25-T01)

Two same-process failures were reproduced before their corresponding fixes:
creating jsconfig after resolving with no config left aliases empty; a valid
config-only tsconfig remap left the persisted changed-context graph pointing at
the original module even after correcting the process alias cache.

Aliases reuse parsed mappings only when the effective readable configuration's
content matches. Readable tsconfig wins over jsconfig, including when its JSON
is invalid. Deleting it falls back to readable jsconfig. Repository-context
cache metadata stores a private content fingerprint and rebuilds relationships
when it changes; old entries lacking that fingerprint rebuild once. Public
reports and MCP schemas stay unchanged. Editing inactive jsconfig preserves
relationships and the repository-context cache hit.

Tests compare complete findings and relationship graphs across cold/warm
changed scans, and complete findings, tiered signals, ChangeProof, evidence
coverage/reasons and decision/next action across an unchanged warm MCP review
and a fresh cold CLI review. The config-only fixture has valid matching exports
at both alias targets; no broken import is invented to produce a signal.
A separate MCP full-scan test compares the whole JSON report after removing
only cache status and measured scan timing. Full and changed scopes retain
their intentional differences. Review contract proof is independently derived
from Git/source evidence; this fix changes resolver reuse and graph freshness,
not proof derivation.

Evidence is local deterministic fixture coverage, not a zoo precision estimate
or a release performance measurement. Config content is read for each alias
resolution to establish freshness; its large-repository overhead is unmeasured.
Concurrent filesystem edits during analysis remain outside snapshot guarantees.
Nested configs, extends inheritance and compiler-complete module resolution are
outside the existing resolver's supported semantics.
